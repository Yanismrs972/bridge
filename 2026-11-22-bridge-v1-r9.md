## 3. Périmètre de la v1 (inchangé, À DÉCIDER D1)

**Inclus :**
- un moteur **destiné à être vérifié en simulation** ;
- l'hôte d'exécution `fake-local` ;
- des projets de démonstration dans `<data>/sim-projects/` ;
- la livraison par **référence Git neuve** ou par **dossier de livraison** ;
- **sous Linux seulement**, et seulement après la qualification QL (§11, D24).

**Exclus :**
- projet réel et Fastclip ;
- Claude et Codex réels, dépense ;
- VM ;
- Windows tant que la série QW n'est pas passée ;
- **modification ou suppression en place d'un fichier de projet** ;
- **quarantaine dans un projet** ;
- intégration automatique dans une branche ;
- push et merge ;
- élévation de permission.

**Modification en place et quarantaine :** BLOQUÉES sans aide native qualifiée (D12) et sans décision explicite (D17).

**Règle de non-suppression, sans exception en v1 :**
- **Bridge ne supprime définitivement aucun fichier ni aucun dossier**, qu'il s'agisse des données de l'utilisateur, des projets de démonstration ou des données internes.
- `destroy` **déplace** les données vers `<data>/retired/` (§7).
- **Aucune commande de purge n'existe en v1.** L'utilisateur vide `<data>/retired/` lui-même, hors de Bridge, s'il le souhaite. C'est la PROPOSITION retenue pour D26.
- Seules exceptions, **qui ne sont pas des suppressions par Bridge** :
  - (a) les fichiers temporaires que **Git** crée et retire lui-même pendant G5 (§8.5) ;
  - (b) les fichiers `-wal` et `-shm` que **SQLite** gère lui-même.

  Leur comportement interne n'est **pas contrôlé** par Bridge, et leurs résidus éventuels sont signalés.

## 4. Architecture, rôles et frontières de confiance

```
┌──────────────────────── PROCESSUS BRIDGE (confiance) ─────────────────────────┐
│ ORCHESTRATEUR (autorité unique)                                               │
│   politiques · permissions · budgets · état · historique · arrêt d'urgence    │
│   confirmations : création, digest, clé K, code, vérification, consommation  │
│   décision d'exécution · SEUL détenteur de l'accès SQLite                     │
│   (y compris process_audit)                                                   │
│   ├── module TerminalConsole (affichage et saisie sur le TTY ; aucune décision)│
│   └── écrivain d'audit : reçoit les événements de lancement de Bridge et les  │
│       écrit de façon durable AVANT de donner le feu vert au lancement         │
│ SERVEUR HTTP (interface) : transmet les demandes ; renvoie les états filtrés  │
│ BRIDGE (transport) : process.ts, adaptateurs, ExecutorHost « fake-local »     │
│   → n'accède JAMAIS à la base ; signale chaque lancement par un rappel et      │
│     attend l'acquittement de l'orchestrateur avant spawn                      │
└───────────────────────────────────────────────────────────────────────────────┘
       ▲ TTY (canal de confiance)                ▲ HTTP 127.0.0.1 (non fiable)
   Terminal de l'utilisateur                 Navigateur
```

| Acteur | Fait | Ne fait jamais |
|---|---|---|
| **Orchestrateur** | Crée les demandes de confirmation ; calcule le contenu canonique et le `digest` ; détient `K` ; tire les codes ; vérifie et consomme les confirmations ; décide de l'exécution ; ordonne à Bridge ; **écrit `process_audit`** à la demande de Bridge, puis acquitte ; enregistre les résultats | Lancer un processus lui-même ; accepter une confirmation venue du serveur |
| **TerminalConsole** | Affiche, après échappement (§13.6), ce que l'orchestrateur lui transmet ; transmet la saisie brute | Décider ; connaître `K` |
| **Serveur HTTP** | Transmet les demandes (créer, annuler, lire un état) ; renvoie des états filtrés | Créer le contenu canonique ; voir `K` ou un code ; valider ; exécuter ; accéder à la base |
| **Bridge** | Exécute les `ProcessSpec` et les `AgentRequest` reçus. **Avant chaque `spawn`**, appelle le rappel `onBeforeSpawn(audit)` fourni par l'orchestrateur et **attend sa réponse**. Si le rappel échoue, aucun lancement | Décider ; accéder à la base |
| **Navigateur** | Émet des demandes ; affiche des états | Confirmer (aucune route) |

Ce découpage corrige r8 §12, où `process.ts` (dans Bridge) écrivait lui-même dans `process_audit`, en contradiction avec r8 §4. Voir A-03.

**Hors modèle :** un logiciel malveillant qui s'exécute sous le compte de l'utilisateur, ou qui contrôle le terminal (§10.1).

## 7. ExecutorHost et isolation

**`fake-local` (v1) :**
- le faux agent est une fonction de Bridge, donc **de confiance** : la séparation qui suit est **conventionnelle** ;
- il travaille dans `<data>/sim-exec/<opId>/` et renvoie un paquet de retour, validé comme hostile (§17).

**`destroy` (v1) :**
- `rename` de `<data>/sim-exec/<opId>/` vers `<data>/retired/sim-exec/<opId>-<horodatage>/`, sur le même volume, à l'intérieur de `<data>` ;
- avant le déplacement : contrôle par `lstat` que la source est un dossier ordinaire créé par Bridge (fichier marqueur `<opId>.bridge` dont le contenu égale l'`opId`) et que la destination est absente ;
- **aucune suppression** ;
- en cas d'échec ou d'état inattendu, l'hôte passe à `unknown`, et toute nouvelle opération est refusée jusqu'à une décision ;
- sous POSIX, `rename` écrase une destination existante. Celle-ci est donc contrôlée juste avant ; la course résiduelle reste **hors modèle** (§10.1) ;
- **Linux :** autorisé après QL-RENAME. **Windows :** BLOQUÉ jusqu'à QW-RENAME.

**Aucune commande de purge en v1** (§3, D26).

**`vm-ssh` (futur) : BLOQUÉ.**
- Le rapport 27 donne comme non testés et bloquants : réseaux `orch-ctl` et `orch-adm`, NAT, pivot vers l'hôte, proxy et exfiltration, `orch-gate` et `orch-priv`, persistance des jetons après restauration [CONSTATÉ].
- WSL2 n'est pas équivalent à une VM.
- **Aucune option applicative n'est une frontière du système d'exploitation.**
- Activation : `R28-ETAPE68-1` (précontrôle), `R28-ETAPE68-2` (laboratoire), plan et audit, QV-1 à QV-7 (annexe A), décision.

### 8.2 Préconditions sur le dépôt (refus sinon)

**Racine et fichiers :**
- `<gitdir>` est un dossier ordinaire (`lstat`). Un fichier `.git` de type `gitdir:` est refusé en v1.
- `objects/`, `objects/info/`, `refs/`, `refs/heads/`, `logs/` et `hooks/` sont absents ou sont des dossiers ordinaires, jamais des liens.
- **Aucun alternate :** `objects/info/alternates` et `objects/info/http-alternates` sont absents [VÉRIFIÉ, `gitrepository-layout.txt`].
- `commondir` est absent (pas de worktree lié en v1).
- `<gitdir>/config` respecte les conditions de §9.3. Aucune clé de stockage de références autre que les fichiers.
- **Chemins :** le chemin de `<gitdir>/objects` ne contient pas le caractère `:` (séparateur de `GIT_ALTERNATE_OBJECT_DIRECTORIES` sous Linux [VÉRIFIÉ]), ni `;` (séparateur sous Windows).

**Hooks** : protection en profondeur, car la priorité de `-c core.hooksPath` sur la configuration locale est **À CONFIRMER** (S122).
- Refus si `hooks/` contient un fichier dont le nom ne se termine pas par `.sample`.
- **Refus inconditionnel** si `hooks/reference-transaction` existe, sous quelque forme que ce soit.
- Statut : PROPOSITION, D28.

### 8.3 Matérialisation de H0 dans Z2

1. **H0** est un OID complet (40 ou 64 caractères hexadécimaux, selon le format). G2 : `rev-parse --verify --end-of-options <H0>^{commit}` [forme VÉRIFIÉE, `git-rev-parse.txt` v2.43.0] doit renvoyer exactement H0.
2. **Liste.** G3 : `ls-tree -r -t -l -z --full-tree --end-of-options <H0>`. Les options `-l` (taille des blobs) et `-t` (entrées d'arbre) sont VÉRIFIÉES (`git-ls-tree.txt`). **Limites appliquées pendant la lecture du flux** (D13, bloquante) :

   | Limite | Valeur |
   |---|---|
   | Entrées | ≤ 20 000 |
   | Profondeur | ≤ 32 |
   | Chemin | ≤ 240 octets UTF-8 |
   | Somme des tailles de blobs annoncées par `-l` | ≤ 200 Mio |
   | Durée de G3 | ≤ 30 s |
   | Sortie de G3 | ≤ 8 Mio |

   Dépassement : refus (`h0_too_large`) et arrêt du processus.
3. **Noms** : sont refusés (`h0_unrepresentable`), sur toutes les plateformes :
   - un UTF-8 invalide, un caractère de contrôle ;
   - un nom réservé Windows (avec ou sans extension) ;
   - l'un des caractères `<>:"|?*\` ;
   - un point ou une espace final ;
   - une collision après NFC et pliage de casse.
4. **Tailles :** une première vérification se fait sur la sortie de `-l`. Un blob de plus de 5 Mio entraîne un refus (`h0_blob_too_large`).
5. **Contenus.** G4 : `cat-file --batch`, dans la cale, **sans** `--filters` ni `--textconv`. Bridge lit l'en-tête `<oid> <type> <taille>\n`, vérifie que la taille est **égale** à celle annoncée par `-l` et qu'elle reste dans les limites, puis lit **exactement** cette taille, puis le saut de ligne. Toute incohérence entraîne un refus et l'arrêt du processus. L'empreinte Git du contenu doit être égale à l'OID.
6. **Écriture dans Z2.** Création exclusive (§10).
   - `100644` : fichier ordinaire.
   - `100755` : `fchmod(0o755)` sous Linux ; aucun bit possible sous Windows.
   - **Le mode de référence est celui du manifeste de Z2**, jamais celui du système de fichiers.
   - `120000` et `160000` : non matérialisés, enregistrés. Toute modification qui les touche est refusée.
7. **Mémoire :** tampons de 1 Mio au plus. **Durée totale :** 120 s au plus.

### 8.4 Construction dans Z5

Toutes ces commandes passent par la cale (§9.2), avec `GIT_OBJECT_DIRECTORY` = Z5 et, en lecture, `GIT_ALTERNATE_OBJECT_DIRECTORIES` = `<gitdir>/objects`.

1. Changements approuvés `{path, action ∈ add/modify/delete/mode_change, sha256, gitMode ∈ 100644/100755}`, appliqués dans Z2 et dans son manifeste.
2. Liste attendue `E`, calculée par Bridge.
3. G5 : `hash-object -w --stdin --no-filters`. L'OID renvoyé doit être égal à l'OID calculé.
4. G6 : `mktree -z`, ce qui donne `T`. G3 sur `T` doit être **exactement** égal à `E`.
5. G7 : `commit-tree -p <H0> --no-gpg-sign -F - <T>` (**les options précèdent l'arbre**, conformément au synopsis VÉRIFIÉ ; corrige r8, A-01).
   - `T` et H0 sont des OID hexadécimaux validés, qui ne commencent jamais par `-`.
   - Variables : `GIT_AUTHOR_NAME`, `GIT_AUTHOR_EMAIL`, `GIT_COMMITTER_NAME`, `GIT_COMMITTER_EMAIL` (D19), et `GIT_AUTHOR_DATE` et `GIT_COMMITTER_DATE` fixés, au format `@<secondes> +0000`, à partir de l'horloge de Bridge, puis enregistrés.
   - Message en UTF-8 : `bridge: <projectId>/<opId> digest=<64 hex>`.
6. **Vérification de `C`** par G4 et analyse par Bridge. L'objet doit contenir **exactement** les en-têtes `tree`, `parent`, `author` et `committer`, dans cet ordre, avec un seul `parent` égal à H0, `tree = T`, et les métadonnées attendues. **Aucun** en-tête `encoding`, `gpgsig` ou `mergetag`. Un écart entraîne un refus.

### 8.5 Transfert et publication (P1 à P6)

**Objets concernés (définition unique) :**
- `F(C)` = `{C}` ∪ `{T}` ∪ tous les arbres et blobs atteignables depuis `T`, obtenus par G3 (`ls-tree -r -t` sur `T`) ;
- plus l'**existence du commit H0**. Les ancêtres de H0 ne sont **pas** vérifiés (limite L-ANC ci-dessous).

| Étape | Action | Effet d'un nettoyage concurrent | Résultat |
|---|---|---|---|
| P1 | Calcul de `N` = objets de `F(C)` absents de Z3, par `cat-file --batch-check` dans la cale avec `GIT_OBJECT_DIRECTORY=<gitdir>/objects` | — | Liste `N` |
| P2 | Pour chaque objet de `N` : lecture brute depuis Z5 (G4, cale Z5), puis **G5-T** `hash-object -w -t <type> --stdin` (cale, `GIT_OBJECT_DIRECTORY=<gitdir>/objects`) [option `-t` VÉRIFIÉE]. L'OID renvoyé doit être égal à l'OID attendu. **C'est Git qui crée l'objet**, Bridge n'écrit aucun fichier dans Z3 | Des objets **déjà présents** dans Z3 et appartenant à `F(C)` (blobs ou arbres partagés avec H0) peuvent être supprimés par un `prune` si **plus aucune référence** ne les atteint. Les objets récents sont protégés par `gc.pruneExpire`, **2 semaines par défaut** [VÉRIFIÉ], **sauf** valeur `now` ou commande forcée | OID égaux |
| P3 | Juste avant G8 : `cat-file --batch-check` sur **tout** `F(C)`, plus H0 (cale, objets de Z3) | Détection | Objet manquant → `objects_missing` : **refus de publier**, aucune modification de référence |
| P4 | G8 : création de la référence (§8.6) | À partir de cet instant, `F(C)` est atteignable, donc protégé par Git | Référence créée |
| P5 | Juste après G8 : même vérification qu'en P3 | **Détection seulement, pas une prévention** | Objet manquant → livraison `corrupt` (§8.8) |
| P6 | Inventaire Z1 et Z3 (§8.7), puis G9 | — | `verified_final`, ou incident |

**Fenêtre exposée :** de la fin de P3 à la fin de P4, plus le transfert P2 pour les objets récents en cas de valeur `now`. Elle est bornée par un délai : **P1 à P5 en 60 s au plus**, sinon refus avant P4, ou marquage après.

**Fichiers temporaires de P2** (exigence B de la mission) :
- Création, écriture, synchronisation et publication sous le nom final : **effectuées par Git lui-même** à l'intérieur de `hash-object -w`. Le mécanisme exact (nom du fichier temporaire, ordre d'écriture, renommage ou lien) n'est **pas documenté** dans les pages consultées : **NON DÉMONTRÉ**.
- **Aucune garantie d'atomicité n'est revendiquée par Bridge.**
- Après un succès : Bridge **vérifie** (P6) qu'aucun fichier dont le nom ne correspond pas au motif d'un objet libre (`objects/xx/<38 ou 62 hex>`) n'a été ajouté.
- **Erreur ou interruption :** l'opération passe à `refused` (erreur) ou `unknown` (interruption). Un **résidu** de fichier temporaire de Git dans `objects/` est **signalé** (`git_tmp_residue`). **Bridge ne le supprime pas.** La page indique qu'un `git gc` ultérieur lancé par l'utilisateur le retirera normalement [DÉDUCTION, À CONFIRMER].
- **Un objet partiellement écrit sous son nom final** (si Git ne publie pas de façon atomique) serait un objet corrompu dans le dépôt. Il est détecté par la relecture P3 et P5, qui exige un contenu cohérent avec l'OID, via `cat-file --batch` dans le cas d'un échec suspect. **Il n'est pas réparé par Bridge.**

**Conditions de refus de la livraison Git :**
- configuration locale avec une clé `gc.*` ou `maintenance.*` (hors liste blanche) ;
- `objects_missing` en P3 ;
- empreinte de configuration changée (§9.3) ;
- délai de 60 s dépassé avant P4 ;
- préconditions de §8.2 non satisfaites ;
- conflit d'arborescence de références (§8.6) ;
- projet bloqué par une livraison `corrupt` (§8.8).

**Après `objects_missing` (P3) :**
- l'opération passe à `refused(objects_missing)` ;
- Z5 conserve ses objets ;
- **aucune relance automatique** ;
- l'utilisateur peut demander une **nouvelle** livraison (nouvel `opId`, nouvelle confirmation), qui refait P1 à P5.

**Limites (limitation déclarée de la v1, NON RÉSOLU) :**
- **L-GC :** un `git gc --prune=now` ou un `git prune --expire=now` de l'utilisateur, ou une configuration globale ou système `gc.pruneExpire=now`, peut supprimer des objets de `F(C)` pendant la fenêtre. Ce cas est détecté en P5, mais **pas empêché**.
- **L-ANC :** si des ancêtres de H0 ont été supprimés (par exemple après un `reset` suivi d'un `prune` de l'utilisateur), l'historique de `C` est incomplet. P3 et P5 ne le détectent pas, puisqu'ils ne vérifient que l'existence de H0. Bridge ne garantit pas l'intégrité de l'historique de l'utilisateur.
- **Conséquence opérationnelle :** pour les projets réels (futur), ces limites relèvent de la décision D23. En v1, sur des projets de démonstration possédés par Bridge, l'exposition est faible.

### 8.6 Publication de la référence et arborescence (P4)

**Validation de l'arborescence avant G8** (lectures `lstat` et G9) :

| Composant | Exigence | Refus |
|---|---|---|
| `refs/` | Dossier ordinaire | Lien, fichier, autre type |
| `refs/heads/` | Dossier ordinaire | Idem |
| `refs/heads/bridge` | **Absent** ou dossier ordinaire. **Aucune** référence nommée exactement `refs/heads/bridge`, ni dans les fichiers ni dans `packed-refs` (vérifié par la liste G9) | Conflit fichier/dossier |
| `refs/heads/bridge/<projectId>` | Absent ou dossier ordinaire ; aucune référence de ce nom exact | Idem |
| `refs/heads/bridge/<projectId>/<opId>` | **Absent** : ni fichier, ni dossier, ni entrée G9, ni `<opId>.lock` | Collision |
| Liens | Aucun composant n'est un lien | Refus |

**G8** (`GIT_DIR=<gitdir>`, options `-c` de §9.5, dont `core.logAllRefUpdates=false` et `core.hooksPath` vide). Flux sur l'entrée standard :
```
start\0
create refs/heads/bridge/<projectId>/<opId>\0<C>\0
prepare\0
commit\0
```
[Syntaxe VÉRIFIÉE, `git-update-ref.txt` v2.43.0 : « create SP <ref> NUL <newvalue> NUL » ; « … Otherwise, no modifications are performed. »]

Git vérifie lui-même les conflits fichier/dossier et l'existence de la référence. Un échec entraîne un refus, sans relance.

**Reflogs :**
- `core.logAllRefUpdates` vaut `true` par défaut dans un dépôt avec dossier de travail [VÉRIFIÉ].
- `-c core.logAllRefUpdates=false` devrait l'emporter [DÉDUCTION, À CONFIRMER, S120].
- Un reflog n'est toléré **que** sous `logs/refs/heads/bridge/<projectId>/<opId>`.

**Interruption pendant G8 :**
- avant `commit` : aucune modification, et un `.lock` éventuel est **signalé, non supprimé** ;
- après : `unknown`, constat par G9, aucune relance.

### 8.7 Inventaire de Z1 et Z3 : portée et limites (exigence F)

**Méthode :** deux photographies, juste avant P1 et en P6.

| Partie | Contenu photographié |
|---|---|
| `<gitdir>` hors `objects/` | Pour chaque entrée : type, taille, `mtime`, `ino` et SHA-256 (fichiers ≤ 1 Mio ; au-delà, taille et `mtime` seulement) |
| `objects/` | Liste des noms de fichiers et dossiers, sans contenu |
| Dossier de travail | Type, taille, `mtime` et `ino` de chaque entrée, **sans empreinte**. Au-delà de 50 000 entrées, la photographie n'est pas prise et la case est marquée **NON VÉRIFIÉ** |

**Différences autorisées entre les deux photographies :**
- `objects/xx/<oid>` pour des OID de `N` ;
- dossiers `objects/xx/` ;
- `refs/heads/bridge/<p>/<op>`, avec le contenu `<C>\n`, et ses dossiers parents ;
- `logs/refs/heads/bridge/<p>/<op>`, seulement si `-c` n'a pas d'effet (S120).

**Tout autre écart est signalé :** `z1_changed` ou `git_tmp_residue`.

**Ce que la comparaison détecte :** les différences **persistantes** entre deux instants, sur les attributs photographiés.

**Ce qu'elle ne peut pas démontrer :**
- les écritures **transitoires** annulées entre les deux photographies ;
- les modifications qui conservent la taille, la date et l'inode dans le dossier de travail (aucune empreinte n'y est calculée) ;
- **l'auteur d'une différence** : une modification faite au même moment par l'utilisateur (commit, changement de branche) produit un écart **non attribuable**. Elle est signalée comme « changement observé, cause indéterminée », **sans conclure** qu'elle vient de Bridge.

L'inventaire est un **contrôle**, pas une preuve d'absence d'écriture.

### 8.8 Machine à états de la livraison Git et cycle de vie de `corrupt`

| État | Persisté avant | Suivant |
|---|---|---|
| `prepared` | — | `materialized` |
| `materialized` | — | `applied` |
| `applied` | — | `built` (G5, G6 et G7 dans Z5, `C` vérifié) |
| `built` | — | `transferred` (P2) |
| `transferred` | — | `checked_pre` (P3) |
| `checked_pre` | — | `published` (P4) |
| `published` | — | `checked_post` (P5) |
| `checked_post` | — | `verified_final` (P6) |
| `refused(raison)`, `unknown`, `corrupt` | — | Terminaux (sauf `unknown` → constat, puis décision) |

Chaque état est persisté (transaction SQLite validée) **avant** l'étape suivante.

**`corrupt`** (objet manquant en P5) :
1. la référence `bridge/<p>/<op>` existe mais désigne un commit incomplet ;
2. **Bridge ne la supprime pas** ;
3. le projet passe à **`blocked_corrupt_delivery`** : **aucune nouvelle livraison et aucune tâche** dont H0 serait ce commit ;
4. le terminal et la page affichent la procédure **manuelle** : l'utilisateur supprime la référence lui-même (`git update-ref -d refs/heads/bridge/<p>/<op> <C>`) ;
5. l'utilisateur déclare ensuite la résolution par une **confirmation hors bande** (`resolve_corrupt`) ;
6. Bridge vérifie par G9 que la référence est absente, puis débloque le projet ;
7. une nouvelle livraison, avec un nouvel `opId` et une nouvelle confirmation, peut alors repartir de la **dernière livraison `verified_final`** ou de H0.

**Limite :** si l'utilisateur ne supprime pas la référence, le projet reste bloqué. C'est voulu.

### 8.9 Rapport de conflits et intégration manuelle
Le rapport de conflits est **inchangé** :
- lecture seule du dossier de travail, sans Git ;
- classement `inchangé`, `modifié par l'utilisateur`, `supprimé` ou `créé` ;
- c'est une photographie, pas une garantie.

L'intégration se fait **par l'utilisateur**. Sans Git, la livraison prend la forme d'un dossier `<data>/deliveries/<opId>/`.

## 9. Commandes Git

### 9.1 Exécutable (QG-1)
- Chemin absolu configuré ; fichier ordinaire situé hors de tout projet.
- Version et SHA-256 qualifiés, puis revérifiés avant chaque usage.
- **Sans qualification : toutes les commandes sont refusées.**

### 9.2 Dépôt « cale »
**G2 à G7, P1 à P3, P5 et G5-T** utilisent :
- `GIT_DIR=<data>/gitshim/<projectId>/` : un dépôt nu créé par Bridge. Son fichier `config`, écrit par Bridge, contient seulement `core.repositoryformatversion`, `core.bare=true` et `extensions.objectformat`, recopiés depuis les valeurs **validées** de §9.3 ;
- `GIT_OBJECT_DIRECTORY` = Z5 (construction) ou `<gitdir>/objects` (transfert et contrôles) [VÉRIFIÉ] ;
- `GIT_ALTERNATE_OBJECT_DIRECTORIES=<gitdir>/objects`, seulement pendant la construction, pour lire les objets de H0. Séparateur interdit dans le chemin (§8.2).

**Effet attendu :** ni `.git/config`, ni ses `include`, ni les hooks, ni les attributs du dépôt de l'utilisateur ne sont lus par ces commandes. Statut : DÉDUCTION à partir de `git.txt`, **À CONFIRMER** par S121.

**Limite :** les fichiers d'objets et les paquets (`pack`) du dépôt de l'utilisateur **sont** lus et analysés par Git. Un paquet malveillant visant une faille d'analyse de Git sort du modèle (R16).

**Seules G1 (sur une copie), G8 et G9** utilisent `GIT_DIR=<gitdir>`.

### 9.3 Configuration : lecture, valeurs, concurrence (exigence D)

**Préconditions sur `<gitdir>/config` :**

| Cas | Traitement |
|---|---|
| Absent | Refus (`config_missing`). Un dépôt normal en possède un |
| Lien, dossier, autre type | Refus (`config_type`) |
| Taille supérieure à 64 Kio | Refus (`config_too_large`) |
| Illisible (droits, verrouillé) | Refus (`config_unreadable`) |
| Fichier ordinaire, 64 Kio au plus | Lecture **unique** par Bridge : ouverture avec `O_NOFOLLOW` (Linux), `fstat` (type et taille), lecture complète, `fstat` à nouveau (taille et `mtime` inchangés, sinon refus `config_unstable`) |

**Copie et analyse :**
- Bridge écrit **ces mêmes octets** dans `<data>/ops/<opId>/config.copy`, par création exclusive.
- G1 est lancé **sur la copie** : `git config --file <copie> --list -z --no-includes` [VÉRIFIÉ : `--no-includes` est le comportement par défaut avec `--file`].
- Il n'y a donc **pas de double lecture** du fichier de l'utilisateur, ce qui corrige A-07.
- `config_digest = SHA-256(octets lus)`.
- La copie contient des valeurs sensibles. Elle reste dans `<data>/ops/<opId>/` et **n'est jamais journalisée**. Elle est retirée avec l'opération (déplacement vers `retired/`, jamais supprimée par Bridge), et **signalée à l'utilisateur** comme contenant sa configuration.

**Valeurs :**
- **Conservés en base :** les noms de clés, `config_digest`, et les trois valeurs validées `core.repositoryformatversion` ∈ {0, 1}, `core.bare` ∈ {true, false} et `extensions.objectformat` ∈ {sha1, sha256}.
- **Jamais conservées, affichées, journalisées, ni renvoyées au navigateur :** toutes les autres valeurs, en particulier `remote.*.url`.
- La sortie standard de G1 reste en mémoire et est effacée après analyse.

**Erreurs :**
- La **sortie d'erreur de G1 n'est jamais conservée** : elle pourrait citer une ligne du fichier. Seuls sont enregistrés le code de sortie et une catégorie fixe (`config_parse_error`).
- Pour G2 à G9, la sortie d'erreur est tronquée à 2 Kio et **masquée** : motif `://[^/@\s]+@` remplacé par `://***@`, ainsi que les motifs de secrets de §26.1. Elle n'est conservée qu'en base, jamais envoyée au navigateur, qui reçoit seulement la catégorie.
- `process_audit` ne contient **jamais** de sortie, seulement l'exécutable, l'empreinte des arguments et le PID.

**Liste blanche** (PROPOSITION, D16) :
- `core.repositoryformatversion`, `core.filemode`, `core.bare`, `core.logallrefupdates`, `core.ignorecase`, `core.precomposeunicode`, `core.symlinks`, `core.autocrlf` ;
- `remote.<n>.url`, `remote.<n>.fetch`, `branch.<n>.remote`, `branch.<n>.merge` ;
- `user.name`, `user.email`, `init.defaultbranch` ;
- `extensions.objectformat`.

**Tout le reste est refusé**, notamment : `include.*`, `includeif.*`, `filter.*`, `diff.*`, `merge.*`, `gc.*`, `maintenance.*`, `core.hookspath`, `core.fsmonitor`, `core.pager`, `core.editor`, `core.sshcommand`, `gpg.*`, `commit.gpgsign`, `credential.*`, `alias.*`, `extensions.refstorage` et les autres `extensions.*`.

**Concurrence :**
- Le fichier est relu (lecture unique, même procédure) et son `config_digest` comparé **avant P1, avant G8 et après G8**. Tout écart entraîne un refus (avant G8) ou un incident (après).
- **Fenêtre résiduelle (R14) :** une modification introduite puis retirée entre deux contrôles n'est pas détectée. Elle n'affecte que G8 et G9, qui reçoivent les neutralisations `-c` (S122). Les commandes d'objets ne lisent pas cette configuration.

## 10. Chemins internes `<data>`

### 10.1 Modèle de menace explicitement réduit
En v1, aucun code non fiable ne s'exécute sous le compte de l'utilisateur pendant que Bridge tourne. Les seuls processus lancés sont :
- `git`, qualifié et passé par la cale ;
- `node`, pour les tests.

Un processus tiers du même compte qui attaquerait `<data>` est **hors modèle**. Les protections ci-dessous visent les **erreurs** et les **états inattendus**, pas un attaquant local actif. **Un élargissement du modèle bloquerait** les écritures dans `<data>` sous Windows, et sous Linux sans aide native (D12).

### 10.2 Contrôles

## 13. Confirmation hors bande (B4, B9, B10)

### 13.1 Canal
Le TTY du processus Bridge (`process.stdin.isTTY === true`, À CONFIRMER sous Windows). **Sans TTY, les actions sensibles sont BLOQUÉES.**

Alternative D6 : `bridge confirm` par un canal local. Non recommandée.

### 13.2 Forme canonique (B10)
- **Encodage :** UTF-8.
- **Objet JSON** dont les clés sont triées par ordre des **points de code** Unicode. Aucun espace.
- **Nombres :** entiers décimaux uniquement, sans flottant.
- **Chaînes :** échappement JSON minimal (`\"`, `\\`, `\uXXXX` pour U+0000 à U+001F) ; aucun autre échappement ; **aucune normalisation Unicode**.
- **Chemins :** transmis sous **deux** formes :
  - `pathBytes`, en base64url des octets exacts ;
  - `pathDisplay`, en texte échappé selon §13.6.

  Le `digest` couvre `pathBytes`.
- **Doublons :** deux entrées dont les `pathBytes` sont égaux, ou égaux après NFC et pliage de casse, entraînent un **refus** de la demande.
- **Contenu de chaque fichier :** `sha256` des octets exacts et `size`.
- **Prompt :** `promptSha256` des octets exacts.

**Structure :** `{v:1, opId, type, scope:{projectId, refName|deliveryDir, h0}, files:[{pathBytes, action, gitMode, size, sha256}], promptSha256|null, limits:{…}, createdAt, expiresAt}`, avec `files` trié par `pathBytes`.

- `digest = SHA-256(octets canoniques)`.
- `proof = HMAC-SHA256(K, "bridge-confirm/v1" ‖ 0x00 ‖ digest ‖ 0x00 ‖ expiresAt)`.
- `K` : 32 octets, en mémoire dans l'orchestrateur, régénérés à chaque démarrage.

### 13.3 Paramètres (À DÉCIDER **D15, bloquante**)

| Paramètre | Valeur proposée, à valider avant implémentation |
|---|---|
| Code | 6 caractères pris dans un alphabet de 32 symboles sans ambiguïté |
| Validité | 3 minutes **de temps passé dans l'écran récapitulatif** ; le décompte est suspendu dans la visionneuse (§13.5) ; plafond absolu de 30 minutes depuis l'émission, visionneuse comprise |
| Tentatives | 3, puis `cancelled` |
| Limites de demandes | 1 en attente par projet, 5 par minute au total, sinon 429 |
| Rejeu | Refusé |
| Redémarrage | Tout ce qui n'est pas `used` devient `expired` |

**Rôle du code :** il impose une lecture délibérée et lie la saisie à une demande. **La sécurité contre une XSS vient de l'absence de toute route de confirmation**, pas du code.

### 13.4 Machine à états : confirmation et opération (B4)

SQLite ne rend **pas** atomiques une transaction et une action du système. Les deux machines sont donc séparées. Chaque transition est une transaction SQLite **distincte, validée (`COMMIT`) avant** l'étape suivante.

| # | Étape | Transaction | État après |
|---|---|---|---|
| C1 | Création de la demande par l'orchestrateur | `INSERT confirmations(state=pending)` | `pending` |
| C2 | Code correct saisi au terminal | `UPDATE … state=confirmed, proof` | `confirmed` |
| C3 | Décision d'exécuter : l'orchestrateur reconstruit le contenu canonique **à partir de l'état actuel**, vérifie le `digest`, la `proof` et l'expiration | Aucune écriture | — |
| C4 | **Consommation et réservation** | `UPDATE confirmations SET state=used` **et** `INSERT operations(state=dispatching, confirmation_id)` dans **une même transaction SQLite** (atomique entre ces deux lignes seulement) | `used` + `dispatching` |
| C5 | Lancement de l'action externe (processus, écriture de fichiers, G8…) | — | — |
| C6 | Démarrage effectif confirmé (PID ou première écriture faite) | `UPDATE operations SET state=running, pid` | `running` |
| C7 | Résultat | `UPDATE operations SET state=completed\|failed\|cancelled\|timed_out` | Terminal |

**Fenêtres de plantage :**

| Plantage entre | Situation | Reprise |
|---|---|---|
| C1 et C2 | Demande non confirmée | `expired` au redémarrage |
| C2 et C4 | Confirmée, non consommée | `expired` (clé `K` perdue). **Aucune exécution** |
| C4 et C5 | Consommée, rien de lancé | Opération `dispatching`, puis `unknown`. Constat : aucun effet attendu observé. **Aucune relance** : une nouvelle confirmation est nécessaire. *La confirmation est perdue : c'est voulu, l'absence de rejeu prime* |
| C5 et C6 | Action peut-être commencée | `unknown`, puis constats (G9, inventaires, PID). Aucune relance |
| C6 et C7 | Action en cours ou terminée | `unknown`, puis constats. Aucune relance |

**Les formulations de r7 sur une « même transaction » pour la consommation et le lancement sont abandonnées.**

### 13.5 Affichage dans le canal de confiance (B10)

**Écran récapitulatif dans le terminal :**
- type d'action, projet, `opId`, H0 complet, référence ou dossier de livraison complet ;
- liste des fichiers : chemin échappé, action, mode, taille, **SHA-256 complet** ;
- empreinte du prompt ;
- limites ;
- **`digest` complet**.

**Visionneuse paginée intégrée** (commandes `v <n>` pour voir le fichier n, `p` pour le prompt, espace pour avancer, `q` pour quitter) :
- affiche le **contenu intégral** de chaque fichier et du prompt exact, page par page (au plus 40 lignes par page), avec la numérotation des lignes ;
- **les contenus ne sont jamais envoyés au navigateur pour approbation** (le navigateur peut afficher un aperçu, mais il n'a aucune valeur d'approbation).

**Règles :**

| Cas | Traitement |
|---|---|
| Contenus binaires | Non transmissibles aux agents. Dans une livraison : affichés en hexadécimal paginé, intégralement |
| Fichier non affichable (encodage invalide, au-delà des limites de §17) | **L'approbation correspondante est BLOQUÉE** |
| Saisie du code | Possible à tout moment. Bridge **affiche**, pour chaque fichier, s'il a été ouvert dans la visionneuse, mais **ne peut pas forcer** la lecture : la responsabilité reste humaine |
| Expiration (précision r9, A-19) | Deux horloges : (1) 3 min cumulées dans l'écran récapitulatif, suspendues dans la visionneuse ; (2) plafond absolu de 30 min depuis l'émission, **qui court toujours**. La première atteinte fait passer la confirmation à `expired` |
| Livraison qui modifie un fichier existant (dossier de livraison neuf ou commit) | La visionneuse affiche, en plus du contenu intégral, un **diff calculé par Bridge** (jamais par un outil externe ni par Git avec pilote externe) entre la version de H0 ou de l'original et la nouvelle, **échappé** selon §13.6. Le diff est une aide de lecture ; seul le contenu intégral et son SHA-256 entrent dans `digest` |

### 13.6 Échappement des données non fiables dans le terminal

Toute donnée non fiable (chemins, contenus, noms de références, messages, sorties) est affichée **après échappement**.

| Catégorie | Rendu |
|---|---|
| Octets ou points de code U+0000 à U+001F (sauf `\n` dans la visionneuse de contenu), U+007F, U+0080 à U+009F | `\xHH` ou `\u{…}` en vidéo inverse |
| Séquences ANSI et ESC (0x1B) | Toujours échappées ; **aucun octet ESC n'atteint le terminal** |
| Caractères bidirectionnels (U+061C, U+200E, U+200F, U+202A à U+202E, U+2066 à U+2069) | `\u{…}` |
| Caractères invisibles (U+200B à U+200D, U+2060, U+FEFF, U+00AD) | `\u{…}` |
| UTF-8 invalide | `\xHH` |
| Retours chariot isolés, tabulations | `\r` ; tabulations rendues en espaces |
| Chemins | Entre guillemets, échappés, avec l'indication « (contient des caractères échappés) » le cas échéant |

## 14. Présentation exacte des contenus

- Les octets transmis (aux faux agents en v1) ou livrés proviennent du magasin, **adressés par leur SHA-256**. Ils sont relus et leur empreinte est recalculée **juste avant** l'usage. Tout écart entraîne un refus et l'invalidation de l'approbation.
- Les éléments exclus sont listés avec leur raison : sensible, inconnu, binaire, trop volumineux, `.git`, lien, refusé par l'utilisateur.
- Le scanner de secrets est une **aide** : « absence de signal ≠ absence de secret ».
- L'utilisateur peut refuser un fichier, ce qui crée une nouvelle demande avec un nouveau `digest`.

### 26.2 Magasin : ordre d'écriture S1 à S7 (r4 §10.2)
1. **S1** : ligne d'opération `dispatched`.
2. **S2** : chaque objet écrit dans `store/tmp`, empreinte calculée pendant l'écriture, puis `fsync`.
3. **S3** : relecture et nouveau calcul de l'empreinte.
4. **S4** : `rename` vers `objects/<aa>/<sha>`, si l'objet est absent. Le contrôle puis `rename` n'est pas atomique en Node (pas de `RENAME_NOREPLACE`) : dans le modèle réduit de §10.1, un écrasement ne peut remplacer un objet que par un contenu de même SHA-256 ; **aucun autre cas n'est garanti**.
5. **S5** : `fsync` du dossier (POSIX, tenté).
6. **S6** : manifeste écrit de la même manière.
7. **S7** : transaction SQLite qui référence le manifeste.

**États de reprise :**

| État | Sens |
|---|---|
| `snapshot_lost` | Manifeste absent |
| `snapshot_corrupt` | Empreinte différente |
| `orphan_manifest` | Ignoré |
| `object_missing`, `object_corrupt` | Chemin non restaurable |

Les fichiers temporaires de `store/tmp` sont retirés vers `<data>/retired/` par la procédure de §7 (déplacement avec marqueur, QL-RENAME), **sans suppression** ; Bridge ne vide jamais `retired/` (D26).
