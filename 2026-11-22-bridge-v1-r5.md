## 3. Architecture retenue

```
                        HÔTE WINDOWS (compte utilisateur)
 ┌───────────────────────────────────────────────────────────────────────────────┐
 │ Navigateur ─HTTP 127.0.0.1 + Authorization─► SERVEUR                          │
 │                                                │                              │
 │                     ORCHESTRATEUR (autorité) ──┤ SQLite, magasin, approbations│
 │                                                │                              │
 │                     BRIDGE (transport) ────────┤ Codex (cwd vide, lecture     │
 │                          │                     │ seule, aucun outil)          │
 │                          │ paquet d'espace (aller) / paquet de résultat       │
 │                          │ (retour) — ExecutorHost                            │
 └──────────────────────────┼────────────────────────────────────────────────────┘
                            │ canal contrôlé (PROPOSITION : SSH vers la VM, compte restreint)
 ┌──────────────────────────▼──────────────────────────┐
 │ VM D'EXÉCUTION (Phase 0B) — Claude Code              │
 │ reçoit uniquement l'espace approuvé ; aucun dossier  │
 │ partagé ; réseau limité aux domaines d'Anthropic     │
 └──────────────────────────────────────────────────────┘
```

**Abstraction `ExecutorHost`** (PROPOSITION) :
```ts
interface ExecutorHost {
  readonly kind: 'fake-local' | 'vm-ssh';
  pushWorkspace(bundle: WorkspaceBundle, signal: AbortSignal): Promise<{ remoteId: string }>;
  runClaude(remoteId: string, req: AgentRequest): Promise<AgentResult>;   // exécution DANS l'hôte isolé
  pullResult(remoteId: string, signal: AbortSignal): Promise<ResultBundle>; // jamais de copie directe vers le projet
  destroy(remoteId: string): Promise<void>;
}
```
- **En v1, seul `fake-local` est implémenté** (simulation : faux Claude dans le processus, espace dans `<data>/sim-exec/`).
- `vm-ssh` est **spécifié mais non implémenté**. Il dépend de la phase VM (§15).

**Rôles** (inchangés) :
- ChatGPT : supervision, cadrage, audit et validation, en dehors de Bridge ;
- Claude Code : seul agent qui écrit ;
- Codex : lecture seule ;
- sous-agents : lecture seule ;
- Bridge : transport, sans aucune décision ;
- orchestrateur : autorité.

**Projets :**
- En v1, la simulation travaille **uniquement** sur des projets de démonstration créés par Bridge dans `<data>/sim-projects/`.
- Toute racine située hors de ce dossier est **refusée**, ce qui exclut l'accès à un projet réel, y compris Fastclip.

## 4. Corrections B1 à B5

### 4.1 B1 — Isolation réelle de Claude

**Constat.** Sous Windows natif, Claude Code s'exécute avec les droits du compte de l'utilisateur.
- `--restricted`, `dontAsk` et les règles de refus sont appliqués **par Claude Code lui-même**. Ce n'est pas une frontière du système d'exploitation.
- Une faille ou un comportement inattendu de la CLI donne accès au projet source, à `<data>`, à `~/.codex`, à `~/.claude` et aux autres projets.
- Le test **Q-PERM** de r4 montre seulement que ces règles fonctionnent pour les essais tentés. **Il ne prouve pas l'absence de contournement** et n'est plus présenté comme suffisant : il devient un contrôle de défense en profondeur **à l'intérieur** de l'environnement isolé.

**Comparaison des isolations possibles**

**Architecture du canal** (PROPOSITION, à mettre en œuvre dans la phase VM, **hors des tâches v1**) :

1. **Aller (`pushWorkspace`).** Le paquet contient le manifeste JSON (chemin, taille, SHA-256, mode Git) et les fichiers approuvés. Il est construit par l'hôte à partir de l'ensemble `transmit_set` approuvé (T8). Il n'y a **jamais** de `.git`, de lien, de fichier non approuvé, ni de chemin absolu.
2. **Exécution.** Claude tourne dans la VM, avec un dossier de travail égal au contenu du paquet. Les arguments sont ceux de §6.3, et l'environnement n'a pas de secret de l'hôte.
3. **Retour (`pullResult`).** Le paquet de résultat est **validé par l'hôte avant tout usage** (T8, `importResultBundle`) :
   1. format strict ; tailles plafonnées (50 Mio au total, 5 Mio par fichier, 5 000 entrées, PROPOSITION) ;
   2. chemins validés (§8.3) ; refus de `.git/**`, des liens, des fichiers spéciaux, des chemins dupliqués à la casse près ;
   3. SHA-256 recalculé à la réception et comparé au manifeste du paquet ;
   4. **fichiers inattendus** (hors de l'espace d'origine et hors des écritures déclarées par Claude) : refus, avec l'incident `unexpected_file` ;
   5. calcul du diff par rapport au paquet d'aller ;
   6. présentation du diff ;
   7. **approbation humaine** `apply_changes`, avec code terminal (§10) ;
   8. application contrôlée au projet source (§8.4).
4. **Nettoyage.** L'espace distant est supprimé, ou bien la VM est restaurée à son snapshot (CONCEPTION Phase 0B).

**Règles :**
- Tant qu'aucune isolation n'est **démontrée** (laboratoire Phase 0B réussi, puis qualifications QV ou QW), Bridge **n'affirme pas** que Claude est confiné.
- **R0 reste BLOQUANT** et le seul hôte d'exécution disponible est `fake-local`. Cela garantit une simulation sans accès au projet réel.
- `vm-ssh` n'est pas implémenté en v1.

**Conditions de qualification de l'isolation (QV, VM) :**
- **QV-1** : aucun dossier partagé, aucun presse-papiers, aucun glisser-déposer. Vérifié dans la configuration de la VM, et par tentative de lecture depuis la VM.
- **QV-2** : des fichiers témoins placés sur l'hôte (projet source, `<data>`, `~/.codex`, `~/.claude`, un autre projet) sont introuvables depuis la VM. On teste les chemins, le réseau (SMB), et le port de Bridge.
- **QV-3** : réseau. Seules les destinations autorisées répondent ; `127.0.0.1:8790` de l'hôte est injoignable.
- **QV-4** : la VM ne contient aucun identifiant de l'hôte.
- **QV-5** : le paquet de retour falsifié (lien, `..`, `.git`, fichier inattendu, empreinte fausse) est refusé par l'hôte.
- **QV-6** : retour au snapshot de la VM après chaque projet ou chaque tâche (choix OUVERT).
- **QV-7** : Q-PERM (fichiers témoins à l'intérieur de la VM), en défense en profondeur.

**Pour WSL2 (QW-1 à QW-6) :** les mêmes contrôles, plus montages désactivés, interopérabilité désactivée, utilisateur sans `sudo`, mode réseau NAT (pas miroir), et vérification que `/mnt/c` est absent.

### 4.2 B2 — Mise à jour Git sans course sur la branche

Détail en §7.

**Principe retenu (PROPOSITION, décision n°4) :** Bridge **ne modifie jamais une référence existante**. Chaque commit approuvé crée **une nouvelle branche** `refs/heads/bridge/<projectId>/<opId>` par une transaction `create`. Elle échoue si la référence existe [VÉRIFIÉ, documentation v2.43.0].

Une branche qui n'existait pas ne peut être extraite dans aucun worktree, et HEAD ne peut pas la désigner. Le changement de branche de l'utilisateur n'a donc **aucun effet** sur l'opération.

L'avance de la branche de l'utilisateur (par exemple `git merge --ff-only bridge/…`) est **faite par l'utilisateur**. C'est conforme à la règle « aucune fusion automatique ».

La mise à jour directe de la branche courante (option B) est **refusée en v1**. Garantir l'atomicité entre HEAD symbolique et référence suppose deux choses :
- `symref-verify` en mode `no-deref`, présent dans la documentation 2.56.1 [VÉRIFIÉ] mais absent de 2.43 ;
- un verrouillage effectif de HEAD pendant `prepare` [À CONFIRMER].

Même dans ce cas, les HEAD des **autres** worktrees ne seraient pas couverts.

### 4.3 B3 — Quarantaine sans suppression

Détail en §8.5.

**Principe retenu (PROPOSITION) :** Bridge **ne supprime jamais** un fichier du projet.
- Une suppression approuvée, une restauration qui retire un fichier, ou un conflit de type deviennent un **déplacement** par `rename` vers `<racine du projet>/.bridge-quarantine/<opId>/<chemin>`, sur le même volume.
- `rename` ne détruit pas de contenu. Un processus qui écrit pendant l'opération, avec un descripteur déjà ouvert, écrit dans le fichier **déplacé**. Sous POSIX, l'écriture par un descripteur ouvert suit l'inode [DÉDUCTION, sémantique `rename(2)`].
- Une copie vérifiée est en plus conservée dans `<data>/store` comme **référence**. Elle **ne conditionne aucune suppression**.
- La suppression définitive de `.bridge-quarantine/` est **manuelle**, faite par l'utilisateur.

### 4.4 B4 — Qualification de Codex en étapes séparées

Détail en §9. Codex reste **BLOQUANT** tant que les niveaux Q0 à Q4 ne sont pas tous réussis. Le premier appel réel (Q5) est une **étape distincte et autorisée**.

### 4.5 B5 — XSS et jeton

Détail en §10. Les règles sont les suivantes :
- aucun rendu de données en HTML ;
- CSP sans `unsafe-inline`, avec Trusted Types ;
- **les actions à fort impact exigent un code affiché dans le terminal**. Un script injecté ne peut donc pas les déclencher seul, même s'il vole le jeton.

## 7. Architecture Git actualisée (B2, B5 de r4 conservé)

### 7.1 Invocations
- `git` est appelé par son chemin absolu, avec un environnement minimal :
  - `GIT_CONFIG_NOSYSTEM=1` [VÉRIFIÉ, doc : ignore le fichier système] ;
  - `GIT_CONFIG_GLOBAL=<fichier vide>` [VÉRIFIÉ, doc : remplace le fichier global] ;
  - `GIT_LITERAL_PATHSPECS=1` [VÉRIFIÉ, doc : pas de globbing ni de pathspec magique] ;
  - `GIT_TERMINAL_PROMPT=0`, `GIT_OPTIONAL_LOCKS=0`.
- Options `-c core.hooksPath=<dossier vide>` [VÉRIFIÉ, doc : dossier des hooks] et `-c core.fsmonitor=false`.
- La configuration **locale** du dépôt (`.git/config`) reste lue par Git. Elle peut définir des filtres (`filter.*.clean`) qui exécutent des programmes lors d'un `hash-object` sur un chemin [À CONFIRMER]. D'où les mesures suivantes :
  - `hash-object -w --stdin --no-filters` (option à vérifier dans `-h` [À CONFIRMER]) ;
  - refus si `.git/config` contient des sections `filter.`, `diff.`, `merge.` avec `driver` ou `textconv`, ou `core.sshCommand` ou `core.editor`. La lecture de `.git/config` se fait par Bridge, en texte, sans l'exécuter.

### 7.2 Construction (inchangée par rapport à r4 §12.2 et §12.3)
- Index temporaire `GIT_INDEX_FILE=<data>/tmp/index-<opId>` [VÉRIFIÉ, doc et expérience].
- `read-tree H0`, `hash-object`, `update-index --cacheinfo`, `update-index --force-remove -z --stdin`, `write-tree`.
- **Modes explicites** dans chaque élément approuvé : `100644` ou `100755` ; `120000` et `160000` refusés.
- Vérification de `diff-tree -r -z --no-renames --raw H0 T` contre la liste approuvée, modes et blobs compris.

### 7.3 Création de la référence (nouveau)

**Préparation :**
- Bridge enregistre `repoTop`, `commonDir` et `H0`.
- `H0` est le commit de base choisi et approuvé, en général le HEAD courant au moment de la préparation. Il **figure dans l'approbation**.
- Nom proposé : `refs/heads/bridge/<projectId>/<opId>`. Il est validé par `git check-ref-format` [À CONFIRMER dans `-h`], sinon par la règle interne `[a-z0-9-]`.

**Transaction (format `-z`, documentation v2.43.0 [VÉRIFIÉ]).** Les octets envoyés sur l'entrée standard de `git update-ref --stdin -z` sont les suivants, où `\0` désigne l'octet NUL :
```
start\0
create refs/heads/bridge/<p>/<op>\0<C>\0
prepare\0
commit\0
```
- `create` vérifie que la référence n'existe pas [VÉRIFIÉ, doc].
- « Otherwise, no modifications are performed » [VÉRIFIÉ, doc].
- Le code de sortie et la sortie d'erreur sont lus. Tout échec (référence existante, verrou présent) entraîne un **refus sans nouvelle tentative**.

**Pourquoi aucune course n'est possible sur la branche :**
- la référence n'existait pas, donc ni HEAD ni aucun worktree ne la désignait ;
- la seule référence modifiée est celle que l'utilisateur a approuvée ;
- HEAD, la branche courante, les autres branches et les worktrees **ne sont jamais écrits**.

**Ce qui reste possible :** un autre processus crée la même référence entre la préparation et la transaction. `create` échoue alors : refus, sans dommage.

**Contrôle postérieur :** `rev-parse --verify refs/heads/bridge/<p>/<op>` doit valoir `C`. Toute autre valeur est un incident ; il n'y a **pas d'action corrective automatique**.

**Effet pour l'utilisateur :**
- Les fichiers approuvés ont été appliqués dans son dossier de travail (§8.4) et apparaissent comme **modifications non commitées** sur sa branche courante.
- Le commit approuvé existe sur la branche `bridge/…`.
- La page propose la commande, **à lancer par l'utilisateur lui-même** : `git merge --ff-only bridge/<p>/<op>`. Une avance rapide n'est possible que si sa branche est toujours à `H0`.
- **L'index réel n'est jamais modifié.** L'effet `MM` de r4 disparaît.

### 7.4 Tests de concurrence (simulation, dépôts de test)
- changement de branche juste avant la transaction → aucun effet sur l'opération, et aucune autre référence modifiée ;
- changement pendant la préparation → idem ;
- branche extraite dans un worktree lié → idem (la référence `bridge/…` est neuve) ;
- référence `bridge/…` créée par un tiers → refus ;
- verrou `refs/heads/bridge/<p>/<op>.lock` présent → refus ;
- arrêt brutal avant `commit` de la transaction → aucune référence créée (« no modifications ») ;
- arrêt brutal juste après → état `unknown`, puis constat de la valeur de la référence ;
- espion : aucune commande `update-ref` autre que `create` sous `refs/heads/bridge/`, et aucun `symbolic-ref`, `checkout`, `switch`, `branch -f`, `merge`, `push` ;
- comparaison des empreintes de toutes les références (`for-each-ref`) avant et après : seule la nouvelle référence diffère.

### 8.3 Chemins et TOCTOU
Reprend r4 §15 (tableau par opération), avec ce complément : la quarantaine et la restauration n'utilisent plus de suppression. Le risque « suppression d'un contenu changé » est donc **éliminé** pour ces opérations. Il **ne disparaît pas** pour l'écriture d'un fichier temporaire puis son `rename` par-dessus la cible.

**Mesure retenue :**
- l'ancienne version de la cible est d'abord **déplacée en quarantaine** (§8.5) ;
- le fichier temporaire est ensuite renommé vers le chemin libéré ;
- si le chemin a été recréé entre-temps, ce que l'on constate **après** le `rename`, l'incident est signalé. Sous POSIX, `rename` aurait écrasé ce nouveau fichier : **risque résiduel**, sans solution en Node faute de `renameat2(RENAME_NOREPLACE)` [DÉDUCTION].

**Alternative plus sûre retenue :**
- pour la création d'un fichier qui n'existait pas, on utilise `open(…, 'wx')` (création exclusive, échec si le fichier existe), puis on écrit et on fait `fsync` ;
- **le `rename` par-dessus une cible n'est jamais utilisé** sur les chemins du projet.

### 8.4 Application des changements au projet (futur mode réel ; en simulation sur les projets de démonstration)

Pour chaque élément approuvé :

| Action | Étapes |
|---|---|
| `modify` | 1. Vérifier que l'empreinte actuelle de la cible est égale à la base (sinon `source_conflict`) ; 2. **déplacer** la cible en quarantaine (§8.5) ; 3. `open(cible, 'wx')`, écrire le contenu approuvé, `fsync`, fermer ; 4. relire et vérifier l'empreinte ; 5. si l'étape 3 échoue parce que le fichier existe (recréé entre-temps), arrêter l'opération et signaler l'incident. Rien n'est perdu : l'original est en quarantaine, le nouveau fichier tiers est intact |
| `add` | `open(cible, 'wx')`. Échec si la cible existe : `source_conflict` |
| `delete` | Déplacement en quarantaine (§8.5) uniquement |
| `mode_change` | Pris en compte au moment du commit uniquement ; le bit lecture seule n'est pas concerné |

### 8.5 Quarantaine (B3)

**Emplacement :** `<racine du projet>/.bridge-quarantine/<opId>/`, créé par `mkdir`. Il est exclusif : `<opId>` est aléatoire, et l'opération échoue si le dossier existe.

`.bridge-quarantine/` est :
- **exclu** des ensembles transmis, des commits (chemin refusé) et du parcours de restauration ;
- inventorié avec le statut `bridge_internal` ;
- signalé à l'utilisateur, qui peut l'ajouter lui-même à `.gitignore`. **Bridge ne modifie pas `.gitignore`.**

**Procédure pour un fichier `p` :**
1. **Journal** : l'opération `quarantine` passe en `dispatched`, avec `{p, sha256_constaté, dest}`, dans une transaction.
2. **Copie de référence** (facultative, n'autorise rien) : lecture et copie vers `<data>/store/…/quarantine-ref/<op>/`, avec empreinte.
3. **Contrôle préalable** : `lstat(p)` doit montrer un fichier ordinaire, pas un lien ; parents vérifiés (r4 §15) ; `realpath(dirname(p))` sous la racine. Un lien ou une jonction est **refusé** : il n'est pas déplacé et est signalé.
4. **Déplacement** : `rename(p, dest)`, sur le même volume, puisque `dest` est sous la racine du projet.
   - Si `rename` échoue (`EXDEV` à cause d'un point de montage dans le projet, `EBUSY`, `EPERM`, fichier ouvert sans partage sous Windows [À CONFIRMER]), **l'original est conservé** et l'état devient `move_refused`.
   - **Aucune copie suivie d'une suppression n'est tentée.**
5. **Contrôle postérieur** : `lstat(p)` doit renvoyer `ENOENT`, sinon le chemin a été recréé, ce qui est signalé sans action. `lstat(dest)` doit montrer un fichier. Son empreinte est recalculée et comparée à `sha256_constaté`. Une différence (modification concurrente) donne `changed_during_move`, signalé. **Le contenu n'est pas perdu** : c'est le fichier déplacé lui-même.
6. **Journal** : `moved` ou `move_refused`, dans une transaction.

**Pourquoi aucune donnée n'est perdue :**
- Bridge ne fait ni `unlink` ni `rm` sur le projet ;
- `rename` ne libère pas le contenu du fichier déplacé ;
- un écrivain concurrent qui tient un descripteur ouvert écrit dans le fichier déplacé (POSIX [DÉDUCTION, sémantique des inodes]).
- Sous Windows, un fichier ouvert sans `FILE_SHARE_DELETE` ne peut pas être renommé : l'erreur entraîne `move_refused` [À CONFIRMER].

**Récupération après interruption :**

| État journalisé | Constat | Action |
|---|---|---|
| `dispatched` | `p` présent, `dest` absent | Rien ne s'est passé : `unknown` puis information |
| `dispatched` | `p` absent, `dest` présent | Le déplacement a eu lieu : `moved_unconfirmed`, information |
| `dispatched` | `p` et `dest` présents | Chemin recréé par un tiers : signalement |
| `dispatched` | `p` et `dest` absents | **Anomalie** (action extérieure) : signalement ; la copie de référence est proposée |

**Coupure électrique :** sous POSIX, le résultat est soit l'ancien nom, soit le nouveau [DÉDUCTION, atomicité de `rename(2)`]. Sous Windows, **À CONFIRMER**.

**Suppression définitive :** **jamais par Bridge**. La page affiche le dossier ; l'utilisateur le vide lui-même.

### 8.6 Tests (simulation, et Windows en phase séparée)
- original modifié pendant l'opération (barrière entre les étapes 3 et 4, puis entre 4 et 5) → contenu présent dans `dest` ;
- fichier remplacé par un lien avant l'étape 4 → refus ;
- parent changé (lien vers l'extérieur) avant l'étape 4 → refus ou incident, sans perte ;
- arrêt brutal après chaque étape → classement du tableau ci-dessus, zéro perte ;
- fichier ouvert en écriture par un autre processus pendant le déplacement → contenu conservé ;
- point de montage dans le projet (`EXDEV`) → `move_refused`, original intact ;
- espion : aucun `unlink` ni `rm` sur le projet ;
- **Windows (QW-RENAME, non exécuté)** : fichier ouvert par un autre programme, avec et sans partage.

`require-trusted-types-for` bloque les « sinks » HTML dans les navigateurs qui le prennent en charge. La liste des navigateurs compatibles est **À CONFIRMER** (MDN inaccessible). Les autres navigateurs reposent sur la règle « aucun sink HTML » et sur le test statique.

### 10.3 Limiter l'impact d'un XSS : code de confirmation dans le terminal (PROPOSITION)

Un script injecté dans l'origine Bridge pourrait lire le jeton ou appeler l'API. Pour réduire cet impact, les actions suivantes exigent un **code à 6 chiffres affiché dans le terminal**, à usage unique, valable 2 min, lié à l'action et à son contenu par une empreinte :
- autorisation de lancement réel ;
- approbation de l'ensemble transmis ;
- approbation du plan ;
- `apply_changes` ;
- `commit_once` ;
- `restore` ;
- `billing_ack` ;
- qualifications ;
- relèvement d'une limite.

Le serveur n'envoie jamais ce code au navigateur. Un script injecté ne peut donc **pas** valider seul ces actions.

Restent possibles pour un XSS : lire les données affichées et déclencher des actions à faible impact (réponses d'entretien, arrêt d'urgence). L'arrêt d'urgence reste sans code : il ne fait qu'arrêter.

- charges XSS via les noms de fichiers, les chemins, les messages d'erreur, les réponses de Claude et de Codex, les événements persistés, les diffs, le diagnostic, les noms de projets et le Markdown → aucune exécution, aucune violation de CSP ;
