## 1. Résumé exécutif

Bridge v1 est **un moteur conçu pour être vérifié en simulation**. Les tests correspondants restent **à écrire et à exécuter**. La v1 n'accède à aucun projet réel, ne lance aucun agent réel et n'appelle ni Codex ni Claude.

**Corrections des quatre blocages de l'audit de r5 :**

| # | Problème | Correction r6 |
|---|---|---|
| B1 | Les modifications pouvaient atterrir dans le checkout actif de l'utilisateur, alors que celui-ci avait changé de branche | **Bridge n'écrit jamais dans le checkout, l'index, HEAD ni une branche existante de l'utilisateur.** Chaque opération a son **propre espace** (`<data>/ops/<opId>/`), matérialisé à partir de H0 par des lectures d'objets brutes. Le commit est construit **sans index ni checkout** (`hash-object`, `mktree`, `commit-tree`), son parent H0 et son arbre sont vérifiés, puis une **nouvelle** référence `bridge/<projet>/<op>` est créée par `update-ref --stdin -z` avec `create`. Le rapatriement vers la branche de l'utilisateur reste **manuel**. |
| B2 | Le couple `lstat` puis `rename` ne garantit pas que le fichier déplacé est celui qui a été contrôlé ; la reprise après interruption n'était pas décrite | **Machine à états persistante par fichier**, avec 11 états, contrôle d'identité **après** le déplacement, création exclusive (`'wx+'`), vérification par le descripteur même, et reprise définie pour chaque état. **Le plan l'énonce sans détour : Node ne permet pas de garantir l'identité jusqu'au déplacement.** Bridge garantit à la place qu'aucun contenu n'est détruit, et il **refuse de poursuivre** dès qu'un écart est constaté. |
| B3 | Git peut exécuter des programmes externes (attributs, filtres, `textconv`, pilotes de diff, `include`, hooks…) | **Liste exhaustive de 9 commandes Git**, toutes de bas niveau, qui ne lisent ni attributs ni filtres dans l'usage prévu, avec leurs options, variables d'environnement et refus. **Liste blanche** des clés de `.git/config`, lue avec `--no-includes`. Neutralisation de `core.hooksPath` (hook `reference-transaction`), GPG, `fsmonitor`, maintenance automatique. Tests avec des programmes témoins malveillants. Les commandes `status`, `diff`, `diff-tree`, `check-ignore`, `checkout`, `add`, `commit` et `worktree` sont **exclues**. |
| B4 | Le code à 6 chiffres pouvait être saisi dans la page, donc capté par une XSS | **Confirmation hors bande dans le terminal de Bridge.** La page crée seulement une *demande*. ## 4. Architecture et responsabilités

```
HÔTE (compte utilisateur)
 Terminal de Bridge (canal de confiance : confirmations hors bande, §13)
 Navigateur ─HTTP 127.0.0.1 + Authorization─► SERVEUR (aucune logique métier)
                                               │
                    ORCHESTRATEUR — autorité : politiques, états, approbations,
                    budgets, preuves, SQLite, magasin, opérations Git et fichiers
                                               │ AgentRequest / ProcessSpec autorisés
                    BRIDGE — transport : adaptateurs, ExecutorHost, lanceur de processus audité
                         │                                    │
                 Codex (v1 : faux)                ExecutorHost « fake-local » (v1)
                                                  [« vm-ssh » : DÉCRIT, non implémenté]
```

| Composant | Responsabilité | Ne fait jamais |
|---|---|---|
| Serveur | HTTP, authentification, création de *demandes* | Décider ; valider une action sensible |
| Terminal de Bridge | Affichage et confirmation des actions sensibles | — |
| Orchestrateur | États, politiques, approbations, Git, fichiers, sauvegardes | Lancer un processus sans passer par Bridge |
| Bridge | Lancer et observer des processus ; adaptateurs | Accéder à la base ; décider |
| Codex | Superviseur, en lecture seule (v1 : faux) | Écrire |
| Claude | Seul agent qui écrit, **dans l'espace d'exécution seulement** (v1 : faux) | Accéder à l'hôte |
| Sous-agents de développement | Relecture en lecture seule | Écrire, commiter |

Un test statique vérifie que `src/bridge` n'importe rien de `src/orchestrator` ni de `src/server`.

## 5. Modèle de sécurité et frontières de confiance

**Non fiables :**
- le contenu des projets ;
- les sorties des agents ;
- les paquets de retour ;
- les entrées HTTP ;
- **le navigateur lui-même** : une XSS est possible, d'où §13 ;
- la configuration Git d'un dépôt (§9) ;
- les autres processus de l'utilisateur.

**De confiance :** le terminal de Bridge, son processus Node et le système d'exploitation. Le terminal est tenu pour fiable **par hypothèse** : un logiciel malveillant capable d'écrire dans ce terminal est hors du modèle.

**Constat inchangé :**
- Sous Windows natif, tout processus du compte de l'utilisateur peut lire et modifier ses fichiers [DÉDUCTION, modèle de droits].
- Les permissions de Claude Code ne forment **pas** une frontière du système d'exploitation. Le bac à sable de Claude Code ne couvre que les commandes, et pas sous Windows natif [DOC sandboxing].

D'où :
- aucun agent réel en v1 ;
- l'usage réel futur passe par une isolation système (§8.3), **NON DÉMONTRÉE**, donc **BLOQUANT**.

## 6. Isolation des projets et des espaces de travail

| Espace | Emplacement | Contenu | Accès |
|---|---|---|---|
| Projets de simulation | `<data>/sim-projects/<projectId>/` | Projets de démonstration, éventuellement avec un dépôt Git créé par Bridge | Orchestrateur |
| Espace d'opération Git | `<data>/ops/<opId>/tree/` | Matérialisation de H0, plus les changements approuvés (§9.3) | Orchestrateur seul ; **jamais** le checkout de l'utilisateur |
| Espace d'exécution | v1 : `<data>/sim-exec/<opId>/` ; futur : VM | Paquet d'aller (fichiers approuvés) | Faux Claude (v1) |
| Magasin | `<data>/store/<projectId>/` | Objets, manifestes, copies de référence | Orchestrateur |
| Quarantaine | `<racine du projet>/.bridge-quarantine/<opId>/` | Fichiers déplacés | Orchestrateur ; l'utilisateur seul supprime |

**Isolation entre projets :**
- chaque table porte `project_id`, et les clés étrangères sont en `RESTRICT` ;
- les espaces sont propres à chaque projet ou à chaque opération ;
- aucun chemin n'est partagé ;
- les budgets et l'historique sont séparés.

**Refus en v1 :** toute racine de projet dont le `realpath` n'est pas sous `realpath(<data>/sim-projects)`, toute racine contenant un lien ou une jonction parmi ses ancêtres, et tout chemin de Fastclip ou d'un autre projet réel.

## 7. Cycle de vie d'une opération

`operations(state)` : `dispatched → running → {completed | failed | cancelled | timed_out}`, plus `unknown`.

Les types d'opération sont : `codex`, `claude`, `fake_*`, `snapshot`, `bundle_out`, `bundle_in`, `file_apply`, `restore`, `quarantine`, `git_commit`, `confirmation`.

Le schéma est le même pour toutes :
1. **Demande** créée par la page ou par le moteur.
2. **Confirmation hors bande** dans le terminal, si l'action est sensible (§13).
3. **Transaction de lancement** (`BEGIN IMMEDIATE`). Elle :
   - vérifie l'état du projet (`running`, et non `stopping`) ;
   - consomme la confirmation (usage unique) ;
   - contrôle les budgets ;
   - insère l'opération en `dispatched`.

   L'index unique `one_active_operation` garantit une seule opération sensible active à la fois.
4. Exécution, avec les **états intermédiaires persistés** propres à chaque type (fichier : §10 ; Git : §9.6).
5. Transaction de fin : état, message `orch/1`, événement.
6. **Redémarrage.** Tout `dispatched` ou `running` devient `unknown`, et Bridge présente l'état constaté. **Aucune relance automatique.** Seules des vérifications en lecture sont faites.

## 8. Exécution des agents et limites de la v1

### 8.1 v1
- `ExecutorHost` `fake-local` uniquement. Le faux Claude est une fonction du processus, qui écrit dans `<data>/sim-exec/<opId>/`.
- Codex : `FakeAdapter`.
- **Aucun chemin de code ne lance `claude` ni `codex` en v1** (vérifié par les tests S41, S95 et S96).

### 8.2 Lancements de processus et interception (C3)
Un faux `PATH` ne voit pas les lancements par chemin absolu. Les contrôles sont donc en couches :
1. **Point unique.** Seul `src/bridge/process.ts` importe `node:child_process`. Un test statique vérifie qu'aucun autre fichier n'importe `node:child_process`, `child_process`, `node:worker_threads` ou `node:vm`, ni n'appelle `process.dlopen`.
2. **Journal d'audit.** `process.ts` enregistre **chaque** lancement (chemin absolu de l'exécutable, empreinte des arguments, PID) dans une table `process_audit`, **avant** l'appel à `spawn`. Les tests vérifient que l'ensemble des exécutables lancés pendant une suite complète en simulation est inclus dans `{git.exe absolu, node de test}`.
3. **Remplacement dans les tests.** `spawn`, `spawnSync`, `execFile`, `execFileSync`, `exec`, `execSync` et `fork` du module `child_process` sont remplacés par des enregistreurs qui échouent. Le test vérifie qu'aucun appel ne contourne `process.ts`.
4. **Modèle de permissions de Node.** Lancer la suite « sans processus » sous `node --permission` **sans** autoriser les processus enfants devrait faire échouer toute création. Le nom exact de l'option dans Node 22 (`--allow-child-process`) est **À CONFIRMER**.
5. **Faux `PATH`** avec des exécutables témoins `codex` et `claude`, en complément seulement.

**Limite déclarée :** un module natif chargé indirectement, ou une dépendance malveillante, sortirait de ces contrôles. D'où la règle de dépendances minimales : `zod` seul en exécution.

### 8.3 Usage réel futur : isolation (C6)
- Isolation système **exigée**. La cible proposée est la **VM de la conception Phase 0B**.
- D'après le rapport `27` (partie 3, points 5 à 9), les éléments suivants ne sont **pas testés** et restent **bloquants** :
  - réseaux `orch-ctl` et `orch-adm` ;
  - option NAT `--nat-localhostreachable1=off` (citée à partir des versions v2 à v6, non relues) ;
  - pivot de la VM vers l'hôte ;
  - proxy squid et risque d'exfiltration ;
  - `orch-gate` et `orch-priv` ;
  - persistance des jetons après restauration.
- **Ils ne sont pas repris ici comme qualifiés.** Le canal SSH de retour, le compte à commande imposée et les règles réseau sont **OUVERTS et NON DÉMONTRÉS**.
- WSL2 n'est pas tenu pour une frontière de sécurité. Il ne serait envisageable qu'après des qualifications dédiées (montages, interopérabilité, réseau en mode miroir, utilisateur sans `sudo` : tous **À CONFIRMER**).

**Limites de `ExecutorHost.destroy` (C8) :**
- `fake-local` supprime `<data>/sim-exec/<opId>/` : ce sont des données internes de Bridge, pas des données de l'utilisateur.
- `vm-ssh` (futur) : retour au snapshot. Le rapport `27` signale que le disque d'identifiants **survit** à la restauration.
- Un échec de `destroy` ⇒ hôte marqué `unknown` ⇒ aucune nouvelle opération sur cet hôte tant que l'utilisateur ne l'a pas décidée.

### 8.4 Codex (C2, C1)
Aucun appel réel en v1.

Pour un usage futur :
- **Un dossier de travail vide ne garantit pas** que Codex ne lise pas d'autres fichiers accessibles au processus. `--sandbox read-only` bloque les écritures, pas les lectures [DÉDUCTION à partir du nom ; À CONFIRMER].
- Restrictions envisagées : options de r5 §9 (`--sandbox read-only`, désactivation des 13 fonctionnalités, `--ignore-user-config`, `--ignore-rules`, `forced_login_method`).
- **Capacités réellement disponibles : À CONFIRMER** par qualification. L'impossibilité d'accéder aux fichiers hors périmètre n'est démontrable qu'en exécutant Codex dans l'environnement isolé, avec des fichiers témoins.
- Codex resterait donc lui aussi dans l'environnement isolé, ou bien une qualification spécifique prouverait l'absence d'outil de lecture.

**Qualification (reprend r5 §9.1, corrigée par C1) :**
- **Q0** (statique) et **Q1 à Q4** (hors ligne) ont pour **précondition humaine** que l'utilisateur déconnecte le PC du réseau (câble, Wi-Fi, mode avion) et le confirme dans le terminal.
- Contrôles **indicatifs** affichés comme tels, et **jamais présentés comme une preuve** :
  - interfaces réseau actives hors boucle locale (`os.networkInterfaces()`) ;
  - échec de résolution DNS d'un nom public ;
  - échec d'une connexion TCP.
- **Un échec de connexion TCP ne prouve pas l'absence de réseau** : DNS, proxy, pare-feu ou filtrage peuvent l'expliquer.
- **Q5**, le premier appel réel, est une étape distincte : autorisation, projet jetable, un appel, supervision, arrêt immédiat en cas d'anomalie, coût **NON DÉMONTRÉ**.

## 9. Modèle Git sécurisé (B1, B3)

### 9.1 Principes
1. **Jamais d'écriture** dans le checkout, l'index (`.git/index`), `HEAD`, une branche existante, la configuration ou les hooks d'un dépôt.
2. **Écritures permises**, purement additives et approuvées :
   - de nouveaux **objets** dans la base d'objets ;
   - **une** nouvelle référence `refs/heads/bridge/<projectId>/<opId>`.
3. Aucune commande de « porcelaine ». Uniquement les 9 commandes de bas niveau de §9.2.
4. Toute propriété non garantie entraîne un **refus**.

**Exclues du chemin critique**, parce que l'absence d'exécution externe n'y est pas démontrée ou qu'elles écrivent l'état de l'utilisateur : `status`, `diff`, `diff-tree`, `log -p`, `show`, `check-ignore`, `check-attr`, `add`, `commit`, `checkout`, `switch`, `restore`, `reset`, `stash`, `merge`, `rebase`, `worktree`, `read-tree`, `update-index`, `write-tree`, `fetch`, `push`, `gc`, `maintenance`.

**Diffs affichés :** ils sont calculés **par Bridge**, en JavaScript, sur les contenus bruts lus par G4 et dans l'espace d'opération. Il n'y a donc ni pilote de diff externe ni `textconv`. Si un `diff` Git devenait nécessaire un jour, il serait lancé avec `--no-ext-diff --no-textconv` [VÉRIFIÉ, `diff-options.txt`], après **qualification**.

### 9.3 Espace d'opération et construction du commit (B1)
1. **Préparation.**
   - G1 (contrôle de la configuration) et G2 (`H0` choisi et inscrit dans l'approbation) ;
   - `commonDir` est relevé et résolu en chemin réel ;
   - G9 : photographie A de toutes les références.
2. **Matérialisation de H0** dans `<data>/ops/<opId>/tree/` :
   - G3 et G4, puis écriture par **Bridge** de chaque blob (création exclusive), sans checkout Git, donc sans `smudge`, hook ni attribut ;
   - les liens (`120000`) sont **enregistrés et non matérialisés** ;
   - un sous-module (`160000`) entraîne un refus si un changement le concerne.
3. **Application des changements** dans l'espace d'opération :
   - éléments approuvés `{path, action ∈ add|modify|delete|mode_change, sha256, gitMode ∈ 100644|100755}` ;
   - les contenus proviennent du paquet de retour validé (§10.6) et sont revérifiés par SHA-256 ;
   - pour `modify` et `delete`, le contenu de H0 dans l'espace d'opération doit correspondre au contenu sur lequel l'approbation a été donnée.
4. **Construction :**
   - G5 pour chaque contenu ajouté ou modifié (empreinte vérifiée avant l'écriture) ;
   - calcul **par Bridge** de la liste complète attendue `E = {(mode, type, oid, chemin)}`, à partir de H0 et des changements ;
   - G6 du bas vers le haut pour chaque répertoire modifié, ce qui donne l'arbre racine `T`.
5. **Vérification de l'arbre.** G3 sur `T` doit produire **exactement** `E`, modes compris. Tout écart entraîne un refus.
6. **Commit.** G7 donne `C`. Ensuite, G4 sur `C`, analysé par Bridge, doit montrer :
   - **un seul parent**, égal à `H0` ;
   - un arbre égal à `T` ;
   - l'auteur et le committer attendus.
7. **Création de la référence.** G8 avec le flux octet par octet `start\0`, `create refs/heads/bridge/<p>/<op>\0<C>\0`, `prepare\0`, `commit\0` [syntaxe VÉRIFIÉE v2.43.0].
8. **Vérification finale.** G9 : photographie B.
   - `B − A` doit être **exactement** `{refs/heads/bridge/<p>/<op> → C}`. Toute autre différence est un incident, sans aucune correction automatique.
   - G2 sur la nouvelle référence doit donner `C`.
9. **Rapatriement.** Il est **manuel**. La page affiche la commande à taper soi-même (`git merge --ff-only bridge/<p>/<op>`, ou `git switch bridge/<p>/<op>`). Aucune fusion automatique.

**Course de branche (scénario de l'audit) :** l'utilisateur peut changer de branche à tout moment, cela n'a **aucun effet**.
- Bridge n'écrit ni dans le checkout ni dans HEAD.
- La référence créée n'existait pas : aucun worktree ne pouvait l'avoir extraite.
- Le parent est fixé par `-p H0` et vérifié à l'étape 6.

### 9.5 Interruptions et références partielles

## 10. Gestion des fichiers et quarantaine (B2, C4)

### 10.1 Portée
La machine à états s'applique à :
- l'**écriture dans un dossier de projet** : projets de simulation en v1, projets réels sans Git à l'avenir ;
- la **restauration** depuis le magasin.

Les projets Git reçoivent leurs changements **uniquement** sous forme de référence (§9). Leur checkout n'est jamais écrit.

### 10.2 Limite fondamentale, déclarée
Node n'offre ni ouverture relative à un descripteur de dossier (`openat`), ni renommage sans écrasement (`RENAME_NOREPLACE`), ni suppression ou renommage par descripteur. Sous Windows, il n'expose pas non plus les modes de partage [DÉDUCTION ; À CONFIRMER pour `UV_FS_O_EXLOCK`].

**Il est donc impossible de garantir que l'objet déplacé est celui qui a été contrôlé.** Bridge garantit à la place trois choses :
- **(i)** aucun contenu n'est détruit : `rename` déplace, et Bridge ne fait jamais `unlink` ni `rm` sur un projet ;
- **(ii)** l'identité et le contenu de l'objet déplacé sont **contrôlés après le déplacement** ;
- **(iii)** dès le moindre écart, l'opération **s'arrête et refuse d'écrire**.

### 10.3 Machine à états d'un élément de fichier (`file_ops`, une ligne par chemin)

**Données persistées :** `op_id`, `path`, `action`, `expected_old {absent | kind, size, mtimeMs, sha256, dev, ino}`, `qdir`, `qpath`, `new_sha256`, `created_identity {dev, ino}`, `state`, `error`, dates.

| État | Opérations pour entrer dans l'état | Données écrites (transaction) **avant** l'étape suivante | Contrôles | Échec |
|---|---|---|---|---|
| F0 `planned` | Approbation confirmée (§13) | Ligne complète, `expected_old` pris dans le snapshot approuvé | Verrou de chemin : index unique sur `(project_id, path)` pour les états non terminaux | Collision avec une autre opération → `X_conflict` |
| F1 `checked` | `lstat(path)` ; ouverture en lecture ; `fstat` ; empreinte ; `lstat` à nouveau | Identité observée `{dev, ino, size, mtime, sha256}` | Fichier ordinaire ; empreinte égale à `expected_old.sha256` ; `dev` et `ino` égaux entre `lstat` et `fstat` ; parents sans lien (`lstat` à chaque niveau) ; `realpath(parent)` sous la racine | Écart → `X_conflict` (aucun déplacement). Pour `add` : `lstat` doit renvoyer `ENOENT`, sinon `X_conflict` |
| F1b `qdir_ready` | `mkdir(<racine>/.bridge-quarantine/<opId>/)` (création exclusive, nom aléatoire) ; `qpath` = dossier + nom unique | `qdir`, `qpath` | `lstat(qpath)` doit renvoyer `ENOENT` | Dossier existant → `X_conflict` |
| F2 `moved` | `rename(path, qpath)` | `state = moved` | **Après** le déplacement : `lstat(qpath)` montre un fichier ordinaire, `dev` et `ino` égaux à F1 (quand disponibles), et l'**empreinte relue** égale à `expected_old.sha256` ; `lstat(path)` renvoie `ENOENT` | `rename` en échec (`EXDEV`, `EPERM`, `EBUSY`, `EACCES`) → `X_move_refused`, rien n'a changé. **Objet déplacé différent** (substitution, lien, jonction, dossier) → `X_moved_unexpected` : **arrêt, aucune écriture**, objet laissé en quarantaine. Chemin recréé par un tiers → `X_conflict` |
| F3 `created` (pour `add` et `modify`) | `open(path, 'wx+')` (création exclusive en lecture et écriture) ; `fstat(fd)` | `created_identity {dev, ino}` | Échec de l'ouverture si le chemin existe | `EEXIST` → `X_conflict` (le fichier du tiers est intact ; l'ancien est en quarantaine) |
| F4 `written` | Écriture complète par le descripteur, puis `fsync(fd)` | `state = written` | Nombre d'octets écrits | Erreur d'écriture → `R_recovery` |
| F5 `verified` | Relecture **par le même descripteur** (position 0), empreinte ; `close` ; `lstat(path)` | `state = verified` | Empreinte égale à `new_sha256` ; `lstat(path)` avec `dev` et `ino` égaux à `created_identity` | Écart → `X_post_write_changed` (le fichier a été remplacé ou modifié après la fermeture) |
| F6 `committed` | Fin de l'opération | `state = committed` | — | — |
| `R_recovery` | — | — | — | Intervention humaine |
| `X_*` | — | Cause | — | Terminal ; intervention humaine |
| `U_unknown` | Redémarrage dans un état non terminal | — | — | Voir §10.4 |

**Action `delete` :** F0, F1, F1b, F2, F6. Bridge ne supprime jamais : la « suppression » est un déplacement.

### 10.4 Reprise après redémarrage
Lectures et constats seulement. **Aucune écriture et aucun déplacement automatiques**, sauf la mise de côté d'un fichier partiel identifié comme créé par Bridge (étape F3/F4 ci-dessous), elle aussi par déplacement non destructif.

| Dernier état persisté | Constat | Classement | Proposé à l'utilisateur |
|---|---|---|---|
| F0 ou F1 | `path` conforme à `expected_old`, rien en quarantaine | `U_unknown`, aucune modification | Relancer comme **nouvelle** opération (nouvelle confirmation) |
| F1b | Idem, `qdir` vide | Idem | Idem |
| F1b | `path` absent, `qpath` présent et conforme | `moved_unconfirmed`, équivalent à F2 | Poursuivre (nouvelle confirmation) ou restaurer |
| F1b | `path` absent, `qpath` présent **non conforme** | `X_moved_unexpected` | Examen humain |
| F2 | `path` absent | Conforme | Poursuivre (nouvelle confirmation) |
| F2 | `path` présent | Tiers ou crash après `open` non persisté → `X_conflict` | Examen ; ne rien toucher |
| F3 ou F4 | `path` d'identité `created_identity` avec une empreinte ≠ `new_sha256` (écriture partielle) | `R_recovery`. Le fichier partiel, **identifié comme le nôtre** (identité égale), est déplacé vers `qdir/partial-…`. L'ancien contenu est dans `qpath` | Restaurer l'ancien (opération `restore`, confirmée) ou recommencer |
| F3 ou F4 | `path` d'identité différente | `X_conflict` | Examen |
| F5 | Empreinte égale à `new_sha256` et identité égale | `verified_unconfirmed` | Confirmer la validation |
| F6 | — | Terminé | — |

**Coupure électrique :** sous POSIX, `rename` donne l'ancien ou le nouveau nom [DÉDUCTION, `rename(2)`]. Sous Windows, **À CONFIRMER**. La durabilité de l'entrée de répertoire n'est **pas démontrée** (§11).

### 10.5 Cas particuliers

| Cas | Traitement | Statut |
|---|---|---|
| Remplacement du fichier source entre F1 et F2 | Détecté en F2 (identité ou empreinte) → `X_moved_unexpected`, aucune écriture ; le fichier substitué est intact en quarantaine | DÉCRIT ; TEST PRÉVU S80 |
| Destination de quarantaine préexistante | Dossier aléatoire créé de façon exclusive. Si `qpath` existe → refus avant le déplacement. **Résiduel :** création par un tiers entre le contrôle et `rename` ; sous POSIX, `rename` écraserait la destination (aucun `RENAME_NOREPLACE` en Node). Le risque est réduit par le nom aléatoire dans un dossier propre à Bridge | Réduit, pas éliminé |
| Lien symbolique ou point de réanalyse substitué | `rename` déplace le lien lui-même, sans suivre la cible ; détecté en F2 | DÉCRIT |
| Création concurrente au chemin d'origine | `open('wx+')` échoue → `X_conflict` | DÉCRIT |
| Écriture partielle | F4 n'est pas atteint ; reprise de §10.4 | DÉCRIT |
| Collision entre deux opérations | Index unique par chemin, plus une seule opération active (§7) | DÉCRIT |

| Suppression définitive | **Jamais par Bridge.** L'utilisateur vide `.bridge-quarantine/` lui-même | — |

### 10.6 Paquets (aller et retour) et limites de ressources (C8)
- **Format v1 :** un manifeste JSON et des fichiers bruts, **sans compression**, donc sans risque de bombe de décompression. Toute compression future exigerait un plafond de taux et de taille décompressée.
- **Plafonds (PROPOSITION) :** 50 Mio au total, 5 Mio par fichier, 5 000 entrées, 240 caractères par chemin, 32 niveaux de profondeur, et manifeste de 2 Mio au plus.
- **Validation du retour :**
  - chemins (règles de r4 et r5, rappelées en §10.7) ;
  - pas de `.git/**`, de lien, de fichier spécial, ni de doublon à la casse près ;
  - SHA-256 recalculés ;
  - fichiers **inattendus** refusés ;
  - écritures déclarées croisées avec les écritures observées.

### 10.7 Chemins, liens et points de réanalyse (C8)
Règles conservées de r4 et r5. Sont refusés :
- les chemins absolus, avec lecteur ou relatifs à un lecteur ;
- les chemins UNC, `\\?\` et `\\.\` ;
- les segments `..` ;
- les deux-points (flux NTFS) ;
- les noms réservés Windows, avec ou sans extension ;
- les points ou espaces finaux ;
- les caractères de contrôle ;
- les collisions de casse ;
- les chemins de plus de 240 caractères.

Les liens et jonctions ne sont **jamais suivis**. Un contrôle par `realpath` sert de second rideau. Le comportement de Node sur les jonctions et les points de réanalyse est **À CONFIRMER** (tests Windows).

## 12. Interface HTTP et sécurité XSS (C8, C7)

**Repris de r5 §10 :**
- jeton porté dans l'en-tête `Authorization`, gardé en mémoire JavaScript, sans cookie ;
- `Host` limité à `127.0.0.1:<port>`, `Origin` obligatoire, aucun en-tête CORS ;
- CSP avec `require-trusted-types-for 'script'` (prise en charge par les navigateurs : À CONFIRMER) ;
- **aucun sink HTML** dans `web/` (test statique) ;
- pas de Markdown ni de lien actif ;
- réponses en JSON seulement ;
- 10 sources d'injection traitées.

**Aperçu du contenu exact transmis (C7, PROPOSITION) :**
- Avant toute approbation de transmission, la page affiche **le contenu intégral** de chaque fichier tel qu'il serait envoyé (texte brut, numéroté, avec son empreinte), et **le texte exact du prompt** construit par Bridge (avec son empreinte).
- L'approbation, confirmée hors bande, est **liée à ces empreintes**. Un contenu modifié rend l'approbation caduque.
- Le résultat du scanner n'est qu'une **aide**. L'approbation porte sur le contenu.
- **En v1, aucune transmission réelle :** les faux agents reçoivent ces contenus localement.

**Ce que XSS peut encore faire :**
- lire les données affichées ;
- créer des *demandes*, sans pouvoir les confirmer (§13) ;
- répondre aux questions d'entretien ;
- déclencher l'arrêt d'urgence.

## 13. Confirmation hors bande (B4)

### 13.1 Canal
Le **terminal qui a lancé Bridge** (`process.stdin` et `process.stdout`), à condition que `process.stdin.isTTY === true` [DÉDUCTION à partir de l'API Node ; comportement exact sous Windows À CONFIRMER].
- Si Bridge tourne sans terminal interactif (service, redirection), **toutes les actions sensibles sont BLOQUANTES**.
- Le navigateur n'a **aucun moyen** d'écrire dans ce terminal.

### 13.2 Déroulement
1. La page envoie une **demande** `POST /api/confirmations {action, params}`. Le serveur calcule le **contenu canonique** de l'action, puis `digest = SHA-256(JSON canonique)`. Il crée `confirmations(id, action, digest, created_at, expires_at, state='pending', attempts=0)`. La page reçoit seulement `{id, état: 'en attente de confirmation dans le terminal'}`.
2. **Le terminal affiche :**
   - le type d'action, le projet, l'identifiant de l'opération ;
   - le **détail exact** : liste des fichiers avec taille, empreinte courte et action ; branche créée, `H0`, nombre de fichiers ; plafonds ; texte de l'avertissement ;
   - le `digest` court (8 caractères) ;
   - l'origine (« demandé depuis la page à HH:MM:SS ») ;
   - un **code de 4 caractères** (alphabet sans ambiguïté), généré aléatoirement et **affiché seulement dans le terminal**.
3. **L'utilisateur tape ce code dans le terminal.** Toute autre saisie compte comme une tentative.
4. Le serveur passe l'état à `confirmed`, avec `proof = HMAC(clé de session du serveur, id ‖ digest ‖ expires_at)`. La clé est en mémoire seulement.
5. **Exécution.** La transaction de lancement (§7) :
   - recalcule le `digest` à partir de l'état **actuel** (fichiers, empreintes, H0) ;
   - vérifie que `proof` est valide et que `state = confirmed` ;
   - vérifie l'expiration ;
   - **consomme** la confirmation (`state = used`).

   Si le `digest` a changé, la confirmation est refusée et une nouvelle demande est nécessaire.

### 13.3 Paramètres (PROPOSITION)

| Paramètre | Valeur |
|---|---|
| Validité | 3 minutes |
| Tentatives par demande | 3, puis `cancelled` |
| Demandes en attente | Une seule par projet ; au plus 5 demandes par minute pour l'ensemble des projets (au-delà, refus HTTP 429) |
| Usage | Unique (`used`). Une preuve ancienne ou rejouée est refusée (état et `proof` liés à l'identifiant) |
| Redémarrage | La clé HMAC est perdue, donc toute confirmation en attente ou confirmée non consommée devient **invalide** (`expired`) |
| Annulation | Saisie de `n` dans le terminal, ou annulation depuis la page (qui ne peut qu'annuler, jamais confirmer) |
| Affichage dans la page | État uniquement, **jamais** le code |

**Actions sensibles concernées :**
- autorisation de lancement réel (futur) ;
- approbation du contenu transmis ;
- validation du plan ;
- application de fichiers ;
- restauration ;
- création de commit et de référence ;
- relèvement d'une limite ;
- `billing_ack` (futur) ;
- qualification Codex (futur).

**Risque restant :** une XSS peut créer une demande trompeuse. La défense est l'affichage complet dans le terminal et la saisie délibérée du code. Une demande non attendue doit être refusée : le terminal porte la mention « Si vous n'êtes pas à l'origine de cette demande, tapez n ».
