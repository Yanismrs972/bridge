## 4. Architecture, rôles et frontières de confiance (B9)

```
┌──────────────────────── PROCESSUS BRIDGE (confiance) ─────────────────────────┐
│ ORCHESTRATEUR (autorité unique)                                               │
│   politiques · permissions · budgets · état · historique · arrêt d'urgence    │
│   confirmations : création, calcul du digest, clé K, code, vérification,      │
│   consommation ; décision d'exécution                                         │
│   ├── module TerminalConsole (affichage et saisie sur le TTY ; aucune décision)│
│   └── accès SQLite (seul détenteur)                                            │
│ SERVEUR HTTP (interface) : transmet des demandes à l'orchestrateur ; renvoie   │
│   les états autorisés ; n'a accès ni à K, ni aux codes, ni à la base           │
│ BRIDGE (transport) : process.ts (lancement audité), adaptateurs, ExecutorHost  │
│   « fake-local » ; reçoit des ordres déjà décidés ; n'accède pas à la base    │
└───────────────────────────────────────────────────────────────────────────────┘
       ▲ TTY (canal de confiance)                ▲ HTTP 127.0.0.1 (non fiable)
   Terminal de l'utilisateur                 Navigateur
```

| Acteur | Fait | Ne fait jamais |
|---|---|---|
| **Orchestrateur** | Crée les demandes de confirmation, calcule le contenu canonique et le `digest`, détient la clé `K`, tire les codes, **vérifie** les saisies, **consomme** les confirmations, **décide** de l'exécution, **ordonne** à Bridge, enregistre les résultats | Exécuter lui-même un processus ; accepter une confirmation venue du serveur |
| **TerminalConsole** (module de l'orchestrateur) | Affiche ce que l'orchestrateur lui transmet (§13.5), échappé ; transmet la saisie brute à l'orchestrateur | Décider ; mémoriser `K` |
| **Serveur HTTP** | Reçoit les demandes du navigateur (créer une demande, annuler, lire un état), les transmet à l'orchestrateur ; renvoie des états **filtrés** | Créer le contenu canonique ; voir `K` ou un code ; valider ; exécuter ; accéder à la base |
| **Bridge** | Exécute des `ProcessSpec` ou des `AgentRequest` reçus de l'orchestrateur ; renvoie des résultats | Décider ; accéder à la base |
| **Navigateur** | Émet des demandes, affiche des états | Confirmer (aucune route ne le permet) |

Ce découpage **corrige r7 §13.3**, qui attribuait au serveur la création, l'affichage, la validation et l'exécution.

**Hors modèle** (B2) : un logiciel malveillant qui s'exécute sous le compte de l'utilisateur, ou qui contrôle le terminal.

**Conséquence assumée :** les courses sur `<data>` provoquées par un tel logiciel ne sont **pas** couvertes (§10).

## 7. ExecutorHost et isolation

**`fake-local` (v1) :**
- le faux agent est une fonction de Bridge, donc **de confiance** : la séparation qui suit est **conventionnelle** ;
- il travaille dans `<data>/sim-exec/<opId>/` et renvoie un paquet de retour, validé comme hostile (§17).

**`destroy` (v1) :**
- `rename` de `<data>/sim-exec/<opId>/` vers `<data>/retired/sim-exec/<opId>-<horodatage>/` (même volume, à l'intérieur de `<data>`) ;
- **aucune suppression** ;
- en cas d'échec, l'hôte passe à `unknown` et toute nouvelle opération est refusée jusqu'à une décision.

**`bridge purge` :** supprime définitivement **uniquement** `<data>/retired/**`, sur confirmation hors bande. L'arbre est parcouru **sans suivre** les liens : un lien rencontré est supprimé comme lien, jamais sa cible. Sous Windows, le comportement exact avec les jonctions est **À CONFIRMER** : **purge BLOQUÉE sous Windows** tant que QW-PURGE n'est pas passé.

**`vm-ssh` (futur) : BLOQUÉ.**
- Le rapport 27 donne comme **non testés et bloquants** : réseaux `orch-ctl` et `orch-adm`, NAT, pivot de la VM vers l'hôte, proxy et exfiltration, `orch-gate` et `orch-priv`, persistance des jetons après restauration [CONSTATÉ].
- WSL2 n'est pas équivalent à une VM.
- **Aucune option applicative** (`--restricted`, `dontAsk`, `--sandbox`) n'est une frontière du système d'exploitation.
- Activation : précontrôle R28-ETAPE68-1, laboratoire R28-ETAPE68-2, plan et audit, qualifications QV-1 à QV-7 (annexe A), décision.

## 8. Git : zones, construction, livraison (B1, B3, B6, B7)

### 8.1 Cinq zones

| Zone | Contenu | Écrit par Bridge ? |
|---|---|---|
| **Z1** Dépôt de l'utilisateur, hors `objects/`, `refs/heads/bridge/` et `logs/refs/heads/bridge/` | Dossier de travail, index, HEAD, branches, configuration, hooks, attributs, `packed-refs`, autres reflogs | **Jamais** |
| **Z2** Espace d'opération `<data>/ops/<opId>/tree/` | Arbre H0 matérialisé et changements | Oui (dossier interne) |
| **Z5** Magasin d'objets de Bridge `<data>/gitobj/<projectId>/objects/` | Blobs, arbres, commit **préparés** | Oui (dossier interne, **jamais nettoyé de façon concurrente**) |
| **Z3** Objets du dépôt de l'utilisateur (`<gitdir>/objects/`) | Copie des objets de Z5 nécessaires, **juste avant** la publication | Oui : **ajout uniquement** de fichiers d'objets et de leurs dossiers `xx/` |
| **Z4** Référence de livraison `refs/heads/bridge/<projectId>/<opId>` | Pointe vers `C` | Oui : création unique |

### 8.2 Préconditions sur le dépôt (refus sinon)
- `gitdir` est un dossier ordinaire. Ni `.git` (s'il s'agit d'un fichier `gitdir:`), ni `objects/`, ni `refs/`, ni `logs/` ne sont des liens ou des jonctions (`lstat`).
- **Aucun alternate :** pas de `objects/info/alternates` ni de `objects/info/http-alternates`. Un alternate ferait lire des objets d'ailleurs [VÉRIFIÉ, `gitrepository-layout.txt`].
- Pas de fichier `commondir` (worktree lié) en v1 : refus.
- Pas de stockage de références autre que les fichiers : `extensions.refstorage` hors liste blanche, donc refusé en G1.
- `core.repositoryformatversion` vaut 0 ou 1 ; `extensions.objectformat` vaut `sha1` ou `sha256`.
- Liste blanche de configuration satisfaite (§9.3).

### 8.3 Matérialisation de H0 dans Z2 (B6)

1. **Identification.** H0 est un **OID complet** (40 ou 64 caractères hexadécimaux, selon le format d'objet). G2, lancé dans la cale (§9.2) avec `--end-of-options <H0>^{commit}`, doit renvoyer **exactement** H0.
2. **Liste.** G3 `ls-tree -r -z --full-tree --end-of-options <H0>` produit des entrées `(mode, type, oid, chemin)`. **Limites appliquées pendant la lecture du flux** (PROPOSITION ; leur validation relève de **D13, bloquante**) :

| Limite | Valeur |
|---|---|
| Entrées | ≤ 20 000 |
| Profondeur | ≤ 32 |
| Longueur d'un chemin (octets UTF-8) | ≤ 240 |
| Taille cumulée annoncée | ≤ 200 Mio |
| Durée de G3 | ≤ 30 s |
| Sortie de G3 | ≤ 8 Mio |

   Au dépassement : **refus** (`h0_too_large`) et arrêt du processus.
3. **Noms.** Chaque chemin doit respecter les règles suivantes, sinon refus (`h0_unrepresentable`), **sur toutes les plateformes**, pour la portabilité :
   - UTF-8 valide ;
   - aucun caractère de contrôle ;
   - aucun nom réservé Windows (`CON`, `PRN`, `AUX`, `NUL`, `COM1` à `COM9`, `LPT1` à `LPT9`, avec ou sans extension) ;
   - aucun des caractères `<>:"|?*\` ;
   - pas de point ni d'espace final ;
   - aucune collision après pliage de casse ou NFC avec un autre chemin.
4. **Tailles.** `cat-file --batch-check` (cale) donne `(oid, type, taille)` **avant** toute lecture. Un blob de plus de 5 Mio entraîne un refus (`h0_blob_too_large`), et le cumul est revérifié.
5. **Contenus.** `cat-file --batch` (cale, **sans** `--filters` ni `--textconv`). Bridge lit l'en-tête `<oid> <type> <taille>\n`, puis **exactement** `taille` octets, puis le saut de ligne. Il **compte** les octets et coupe si l'en-tête est incohérent. L'empreinte Git du contenu est recalculée et doit être égale à l'OID.
6. **Écriture dans Z2.** Création exclusive (`'wx'`) dans des dossiers créés par Bridge (§10).
   - **Modes :**
     - `100644` : fichier ordinaire ;
     - `100755` : sous Linux, `fchmod(0o755)` sur le descripteur ; sous Windows, aucun bit possible ;
     - **dans les deux cas, le mode de référence est celui du manifeste de Z2 tenu par Bridge**, pas celui du système de fichiers. Le commit est construit à partir du manifeste.
   - `120000` (lien) et `160000` (sous-module) : **non matérialisés**, enregistrés dans le manifeste. Toute modification qui les touche est refusée.
7. **Mémoire.** Les lectures se font en flux, avec un tampon de 1 Mio au plus par blob.
8. **Durée totale** de la matérialisation : 120 s au plus, sinon refus.

### 8.4 Construction dans Z5 (avant tout contact avec Z3)
1. Changements approuvés `{path, action ∈ add/modify/delete/mode_change, sha256, gitMode ∈ 100644/100755}`, appliqués dans Z2 et dans son manifeste.
2. Liste attendue `E`, calculée par Bridge.
3. G5 `hash-object -w --stdin --no-filters`, **avec `GIT_OBJECT_DIRECTORY` = Z5** (cale). L'OID renvoyé doit être égal à l'OID calculé.
4. G6 `mktree -z` (cale, Z5, avec `GIT_ALTERNATE_OBJECT_DIRECTORIES` = objets du dépôt **en lecture**, pour les arbres et blobs de H0 réutilisés). Résultat : `T`.
5. G3 sur `T` (cale) doit être **exactement** égal à `E`.
6. G7 `commit-tree --end-of-options <T> -p <H0> --no-gpg-sign -F -` (cale, Z5, alternates en lecture). G4 sur `C` : **un seul parent, égal à H0**, `tree = T`, métadonnées attendues (D19).

Tant que la construction a lieu dans Z5, **un `gc` du dépôt de l'utilisateur ne peut pas toucher ces objets**, car ils n'y sont pas.

|---|---|---|---|
| P1 | Liste `N` des objets à transférer : les blobs, les arbres et `C` de Z5 **absents** de Z3. Vérification par `cat-file --batch-check` sur le dépôt, en lecture | — | — |
| P2 | Copie par Bridge de chaque fichier d'objet libre de Z5 vers `<gitdir>/objects/xx/` : fichier temporaire dans `objects/xx/`, `fsync`, `link` ou création exclusive vers le nom final (un objet déjà présent n'est jamais remplacé ; même contenu, même nom) | Les objets sont **récents**. `gc` ne supprime les objets libres non référencés que s'ils sont plus anciens que `gc.pruneExpire`, soit **2 semaines par défaut** [VÉRIFIÉ, `config/gc.txt`]. **Ce n'est pas une garantie** : la valeur `now`, ou un `git prune --expire=now` manuel, les supprimerait | — |
| P3 | **Juste avant G8** : `cat-file --batch-check` sur **tous** les objets atteignables depuis `C` qui sont absents de H0 (dépôt, lecture) | Détection | **Refus de publier** (`objects_missing`) ; rien n'est publié |
| P4 | G8 : création de la référence (§8.6) | Une fois la référence créée, les objets sont atteignables et protégés de `gc` | — |
| P5 | **Après G8** : nouvelle vérification de l'existence de tous ces objets | Détection d'une suppression entre P3 et P4 | La livraison est marquée **`corrupt`**. La référence reste, puisque Bridge ne supprime rien. **Message à l'utilisateur** : supprimer la référence lui-même (`git update-ref -d refs/heads/bridge/<p>/<op>`), puis relancer avec une nouvelle confirmation |

**Conditions de refus de la livraison Git :**
- la configuration locale contient une clé `gc.*` ou `maintenance.*` (hors liste blanche) ;
- un objet manque en P3 ;
- l'empreinte de la configuration a changé (§9.3) ;
- P1 à P5 durent plus de 60 s ;
- des préconditions de §8.2 ne sont plus satisfaites.

**Risque résiduel déclaré (NON RÉSOLU) :** un `git gc --prune=now` ou un `git prune --expire=now` lancé par l'utilisateur, ou une configuration **globale ou système** de l'utilisateur avec `gc.pruneExpire=now`, peut supprimer des objets entre P2 et P4.
- **Détection :** P5 (livraison marquée `corrupt`).
- **Prévention :** impossible sans contrôler les processus de l'utilisateur.
- **En v1** (projets de démonstration possédés par Bridge), l'exposition est faible. **Pour les projets réels, c'est une décision** : D23.

### 8.6 Publication de la référence et inventaire des écritures (B3)

**G8**, lancé avec `GIT_DIR=<gitdir>` (dépôt de l'utilisateur) et les options `-c` de §9.2, **dont `core.logAllRefUpdates=false`**. Flux sur l'entrée standard :
```
start\0
create refs/heads/bridge/<projectId>/<opId>\0<C>\0
prepare\0
commit\0
```
[Syntaxe VÉRIFIÉE, `git-update-ref.txt` v2.43.0 : « create SP <ref> NUL <newvalue> NUL » ; « If all <ref>s can be locked with matching <oldvalue>s simultaneously, all modifications are performed. Otherwise, no modifications are performed. »]

**Reflogs.**
- `core.logAllRefUpdates` vaut `true` par défaut dans un dépôt avec dossier de travail, et crée alors `logs/<ref>` pour les branches [VÉRIFIÉ].
- `-c core.logAllRefUpdates=false` passé en ligne de commande devrait l'emporter sur la configuration locale [DÉDUCTION à partir de la priorité des options `-c` ; **À CONFIRMER**, test S120].
- Si un reflog apparaît malgré tout, l'écart est **toléré seulement** pour `logs/refs/heads/bridge/<projectId>/<opId>`. Tout autre reflog modifié est un incident.

**Écritures autorisées dans le dépôt** (comparaison des inventaires avant et après, par empreinte de chaque fichier) :

| Chemin | Changement autorisé |
|---|---|
| `objects/xx/<reste de l'oid>` | **Ajout** seulement, pour des OID de la liste `N` |
| `objects/xx/` | Création de dossier |
| `objects/xx/tmp_*` ou autres temporaires | **Aucun ne doit subsister.** Un résidu est un incident, signalé et non supprimé |
| `refs/heads/bridge/`, `refs/heads/bridge/<p>/` | Création de dossier |
| `refs/heads/bridge/<p>/<op>` | Création, avec le contenu `<C>\n` |
| `refs/heads/bridge/<p>/<op>.lock` | **Ne doit pas subsister.** Un résidu (interruption) est signalé, jamais supprimé par Bridge |
| `logs/refs/heads/bridge/<p>/<op>` et ses dossiers | Toléré seulement si `logAllRefUpdates` n'a pas été neutralisé (S120) |
| **Tout autre chemin** : index, HEAD, `packed-refs`, `config`, autres `refs/`, autres `logs/`, `hooks/`, `info/`, `objects/pack/`, `objects/info/` | **Aucun changement.** Sinon : incident `z1_modified` |

**Interruption pendant G8 :**
- **avant `commit`** : aucune modification (« no modifications ») ; un `.lock` éventuel est signalé ;
- **après** : la référence existe. Au redémarrage, l'état constaté est `unknown`, avec G9 pour la constatation. **Aucune relance automatique.**

**Référence déjà existante :** `create` échoue et le refus est enregistré. Un nouvel `opId` exige une nouvelle confirmation.

**Évolution du dépôt pendant l'opération** : changement de branche ou de HEAD, nouveau worktree, nouvelles références. Ces événements sont **sans effet** sur `C`, dont le parent est fixé à H0, et sont seulement reflétés dans le **rapport de conflits**, établi en lecture seule (§8.7).

**Ce que la transaction ne protège pas :** elle ne protège **que** les références. La protection de Z1 vient de l'absence d'écriture de Bridge, vérifiée par l'inventaire.

### 8.7 Rapport de conflits et intégration manuelle
- Pour chaque chemin touché, Bridge lit le fichier dans le dossier de travail **sans Git et sans écrire**. Il le compare au contenu de H0 et au contenu approuvé, ce qui donne : `inchangé`, `modifié par l'utilisateur`, `supprimé` ou `créé`. Il signale aussi la branche actuellement extraite. C'est une **photographie** à un instant donné, pas une garantie.
- **Intégration :** commandes affichées, **à lancer par l'utilisateur**. Aucune branche existante n'est avancée par Bridge.
- **Sans Git :** dossier de livraison `<data>/deliveries/<opId>/`, contenant l'arbre, le manifeste et le patch ; application manuelle.

## 10. Chemins internes `<data>` (B2)

### 10.1 Modèle de menace explicitement réduit
En v1, aucun code non fiable ne s'exécute sous le compte de l'utilisateur pendant que Bridge tourne. Les seuls processus lancés sont :
- `git`, qualifié, et neutralisé par la cale ;
- `node`, pour les tests.

Les faux agents sont du code de Bridge. Un processus tiers du même compte qui attaquerait `<data>` est **hors modèle** (§4).

**Conséquence :** les protections ci-dessous visent les **erreurs**, les **états inattendus** et les **objets hérités** (liens laissés dans `<data>`). Elles ne visent **pas** un attaquant local actif. **Si le modèle de menace était élargi, les fonctions qui écrivent dans `<data>` seraient BLOQUÉES** sous Windows, et sous Linux sans aide native (D12).

### 10.2 Contrôles

| Contrôle | Moment | Linux | Windows |
|---|---|---|---|
| `<data>` est un dossier ordinaire ; `realpath(<data>)` est égal au chemin configuré ; aucun ancêtre n'est un lien | Démarrage | `lstat` de chaque ancêtre | `lstat` ; comportement sur les jonctions **À CONFIRMER**, contrôle `realpath` en second rideau |
| Sous-dossiers `ops`, `sim-exec`, `deliveries`, `store`, `gitobj`, `gitshim`, `git-cwd`, `retired`, et le dossier SQLite : dossiers ordinaires créés par Bridge, jamais des liens | Démarrage et avant chaque usage | `lstat` | `lstat` (jonctions À CONFIRMER) |
| Création d'un dossier d'opération | Lancement | `mkdir` non récursif, qui échoue s'il existe ; puis `lstat` : dossier ordinaire ; `realpath` sous `<data>` | Idem |
| Création d'un fichier | — | `open(…, O_CREAT\|O_EXCL\|O_NOFOLLOW)` : aucun écrasement, aucun lien suivi sur le dernier composant [constantes VÉRIFIÉES] | `'wx'` (création exclusive : **À CONFIRMER**) ; **pas d'`O_NOFOLLOW`** |
| Parent remplacé entre le contrôle et la création | — | **Non empêché en Node** (pas d'`openat`). Détecté après coup par `realpath(parent)` et `lstat` | Idem |
| Fichiers SQLite (`bridge.db`, `-wal`, `-shm`) | Démarrage | `lstat` : fichiers ordinaires ou absents | Idem |
| Chemin sortant de la racine autorisée | Toute construction de chemin | Construction par jonction de segments validés (§8.3) ; aucun `..` ; vérification `realpath` sous `<data>` | Idem |

**Limite :** la simple création d'un dossier neuf **n'est pas** présentée comme une protection suffisante contre un attaquant. Elle ne l'est que dans le modèle réduit de §10.1.

## 12. Processus

**Lancement :**
- `src/bridge/process.ts` est le seul module qui importe `node:child_process` (test statique).
- `spawn(exe, args, {shell: false, windowsHide: true})`, avec `exe` en chemin absolu, pris dans une liste fermée (v1 : `git` qualifié ; `node` pour les tests).
- Environnement reconstruit.
- `process_audit` écrit **avant** `spawn` : exécutable, empreinte des arguments, PID. **Jamais la sortie.**

**Barrières :** état `stopping`, contrôle de `signal.aborted` avant `spawn`, nouveau contrôle lors de l'enregistrement du PID. Un lancement pendant l'arrêt entraîne un arrêt immédiat, puis `cancelled`.

| Situation | Linux | Windows | Garantie |
|---|---|---|---|
| Délai dépassé ou arrêt | `SIGTERM` au groupe, puis `SIGKILL` après 5 s | `taskkill /PID /T /F` | — |
| Preuve de terminaison | `kill(-pgid, 0)` renvoie `ESRCH` : `verified` | Aucune : `unverified` | **Un `kill` ne prouve pas la fin des descendants** |
| Orphelin qui quitte le groupe | Non détecté | Non détecté sans Job Object (D22) | NON DÉMONTRÉ |
| Processus qui refuse de se terminer | `SIGKILL`, puis `stuck` | `/F`, puis `stuck` si le PID existe toujours | Signalé ; aucune boucle |
| Arrêt de Bridge | Les enfants survivent | Idem | Au redémarrage : « peut-être actif » (PID et date de démarrage) ; rien n'est tué sans décision |
| Arrêt forcé pendant une opération | États persistés ; constats | Idem | — |

**En v1 :** des `git` de courte durée seulement, un processus enfant à la fois.

## 13. Confirmation hors bande (B4, B9, B10)

### 13.1 Canal
Le TTY du processus Bridge (`process.stdin.isTTY === true`, À CONFIRMER sous Windows). **Sans TTY, les actions sensibles sont BLOQUÉES.**

Alternative D6 : `bridge confirm` par un canal local. Non recommandée.

### 13.2 Forme canonique (B10)
- **Encodage :** UTF-8.
- **Objet JSON** dont les clés sont triées par ordre des **points de code** Unicode. Aucun espace.
- **Nombres :** entiers décimaux uniquement, sans flottant.
- **Chaînes :** échappement JSON minimal (`\"`, `\\`, `\uXXXX` pour U+0000 à U+001F) ; aucun autre échappement ; **aucune normalisation Unicode**.
- **Chemins :** transmis sous **deux** formes :
  - `pathBytes`, en base64url des octets exacts ;
  - `pathDisplay`, en texte échappé selon §13.6.

  Le `digest` couvre `pathBytes`.
- **Doublons :** deux entrées dont les `pathBytes` sont égaux, ou égaux après NFC et pliage de casse, entraînent un **refus** de la demande.
- **Contenu de chaque fichier :** `sha256` des octets exacts et `size`.
- **Prompt :** `promptSha256` des octets exacts.

**Structure :** `{v:1, opId, type, scope:{projectId, refName|deliveryDir, h0}, files:[{pathBytes, action, gitMode, size, sha256}], promptSha256|null, limits:{…}, createdAt, expiresAt}`, avec `files` trié par `pathBytes`.

- `digest = SHA-256(octets canoniques)`.
- `proof = HMAC-SHA256(K, "bridge-confirm/v1" ‖ 0x00 ‖ digest ‖ 0x00 ‖ expiresAt)`.
- `K` : 32 octets, en mémoire dans l'orchestrateur, régénérés à chaque démarrage.

### 13.3 Paramètres (À DÉCIDER **D15, bloquante**)

| Paramètre | Valeur proposée, à valider avant implémentation |
|---|---|
| Code | 6 caractères pris dans un alphabet de 32 symboles sans ambiguïté |
| Validité | 3 minutes |
| Tentatives | 3, puis `cancelled` |
| Limites de demandes | 1 en attente par projet, 5 par minute au total, sinon 429 |
| Rejeu | Refusé |
| Redémarrage | Tout ce qui n'est pas `used` devient `expired` |

**Rôle du code :** il impose une lecture délibérée et lie la saisie à une demande. **La sécurité contre une XSS vient de l'absence de toute route de confirmation**, pas du code.

### 13.4 Machine à états : confirmation et opération (B4)

SQLite ne rend **pas** atomiques une transaction et une action du système. Les deux machines sont donc séparées. Chaque transition est une transaction SQLite **distincte, validée (`COMMIT`) avant** l'étape suivante.

| # | Étape | Transaction | État après |
|---|---|---|---|
| C1 | Création de la demande par l'orchestrateur | `INSERT confirmations(state=pending)` | `pending` |
| C2 | Code correct saisi au terminal | `UPDATE … state=confirmed, proof` | `confirmed` |
| C3 | Décision d'exécuter : l'orchestrateur reconstruit le contenu canonique **à partir de l'état actuel**, vérifie le `digest`, la `proof` et l'expiration | Aucune écriture | — |
| C4 | **Consommation et réservation** | `UPDATE confirmations SET state=used` **et** `INSERT operations(state=dispatching, confirmation_id)` dans **une même transaction SQLite** (atomique entre ces deux lignes seulement) | `used` + `dispatching` |
| C5 | Lancement de l'action externe (processus, écriture de fichiers, G8…) | — | — |
| C6 | Démarrage effectif confirmé (PID ou première écriture faite) | `UPDATE operations SET state=running, pid` | `running` |
| C7 | Résultat | `UPDATE operations SET state=completed\|failed\|cancelled\|timed_out` | Terminal |

**Fenêtres de plantage :**

| Plantage entre | Situation | Reprise |
|---|---|---|
| C1 et C2 | Demande non confirmée | `expired` au redémarrage |
| C2 et C4 | Confirmée, non consommée | `expired` (clé `K` perdue). **Aucune exécution** |
| C4 et C5 | Consommée, rien de lancé | Opération `dispatching`, puis `unknown`. Constat : aucun effet attendu observé. **Aucune relance** : une nouvelle confirmation est nécessaire. *La confirmation est perdue : c'est voulu, l'absence de rejeu prime* |
| C5 et C6 | Action peut-être commencée | `unknown`, puis constats (G9, inventaires, PID). Aucune relance |
| C6 et C7 | Action en cours ou terminée | `unknown`, puis constats. Aucune relance |

**Les formulations de r7 sur une « même transaction » pour la consommation et le lancement sont abandonnées.**

### 13.5 Affichage dans le canal de confiance (B10)

**Écran récapitulatif dans le terminal :**
- type d'action, projet, `opId`, H0 complet, référence ou dossier de livraison complet ;
- liste des fichiers : chemin échappé, action, mode, taille, **SHA-256 complet** ;
- empreinte du prompt ;
- limites ;
- **`digest` complet**.

**Visionneuse paginée intégrée** (commandes `v <n>` pour voir le fichier n, `p` pour le prompt, espace pour avancer, `q` pour quitter) :
- affiche le **contenu intégral** de chaque fichier et du prompt exact, page par page (au plus 40 lignes par page), avec la numérotation des lignes ;
- **les contenus ne sont jamais envoyés au navigateur pour approbation** (le navigateur peut afficher un aperçu, mais il n'a aucune valeur d'approbation).

**Règles :**

| Cas | Traitement |
|---|---|
| Contenus binaires | Non transmissibles aux agents. Dans une livraison : affichés en hexadécimal paginé, intégralement |
| Fichier non affichable (encodage invalide, au-delà des limites de §17) | **L'approbation correspondante est BLOQUÉE** |
| Saisie du code | Possible à tout moment. Bridge **affiche**, pour chaque fichier, s'il a été ouvert dans la visionneuse, mais **ne peut pas forcer** la lecture : la responsabilité reste humaine |
| Expiration | Elle **s'interrompt** pendant la consultation : elle ne court que dans l'écran récapitulatif, avec un plafond total de 30 minutes |

### 13.6 Échappement des données non fiables dans le terminal

Toute donnée non fiable (chemins, contenus, noms de références, messages, sorties) est affichée **après échappement**.

| Catégorie | Rendu |
|---|---|
| Octets ou points de code U+0000 à U+001F (sauf `\n` dans la visionneuse de contenu), U+007F, U+0080 à U+009F | `\xHH` ou `\u{…}` en vidéo inverse |
| Séquences ANSI et ESC (0x1B) | Toujours échappées ; **aucun octet ESC n'atteint le terminal** |
| Caractères bidirectionnels (U+061C, U+200E, U+200F, U+202A à U+202E, U+2066 à U+2069) | `\u{…}` |
| Caractères invisibles (U+200B à U+200D, U+2060, U+FEFF, U+00AD) | `\u{…}` |
| UTF-8 invalide | `\xHH` |
| Retours chariot isolés, tabulations | `\r` ; tabulations rendues en espaces |
| Chemins | Entre guillemets, échappés, avec l'indication « (contient des caractères échappés) » le cas échéant |

## 14. Présentation exacte des contenus

- Les octets transmis (aux faux agents en v1) ou livrés proviennent du magasin, **adressés par leur SHA-256**. Ils sont relus et leur empreinte est recalculée **juste avant** l'usage. Tout écart entraîne un refus et l'invalidation de l'approbation.
- Les éléments exclus sont listés avec leur raison : sensible, inconnu, binaire, trop volumineux, `.git`, lien, refusé par l'utilisateur.
- Le scanner de secrets est une **aide** : « absence de signal ≠ absence de secret ».
- L'utilisateur peut refuser un fichier, ce qui crée une nouvelle demande avec un nouveau `digest`.
